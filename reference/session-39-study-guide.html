Diagnosticar AEM Cloud con la herramienta adecuada

Logs, Developer Console, Repository Browser y RDE aplicados a una hipótesis concreta.

  • 30 minutos · caso simulado
  • Descargar Markdown completo
  • Slides en inglés
Objetivo: ante un 500 en Publish que no ocurre en Author, elegir la siguiente herramienta, citar la evidencia y formular una conclusión limitada por ella. Todos los resultados y nombres del caso son inventados; no se necesita acceso Cloud ni despliegue.

2. Caso guiado: 200 en Author, 500 en Publish

Ficha didáctica inventada. /content/wknd/en/guides.html devuelve 200 en Author y 500 en Publish. Se investiga Publish; la diferencia no demuestra que código, configuración y contenido sean iguales entre tiers.

Logs de Publish

14:05:17 GET /content/wknd/en/guides.html 500
14:05:17 ERROR GuideListModel: CatalogService unavailable

Selecciona el ambiente y servicio, luego acota por ruta y hora. En un caso real correlaciona además el identificador de petición o contexto; compartir hora no prueba causalidad. CatalogService unavailable estrecha la búsqueda, pero no indica aún si faltó un bundle, una configuración u otra dependencia. Acceso a logs — Adobe.

3. RDE: flujo teórico para probar una hipótesis

RDE permite sincronizar rápidamente código, configuración y contenido desde herramientas locales. Esta sección es teórica: no hay un RDE disponible para esta clase. Un equipo con acceso intentaría primero reproducir el 500 con artefactos y datos comparables; después aplicaría una corrección candidata y comprobaría la respuesta HTTP y el estado del componente. Si no se reproduce el fallo inicial, un 200 posterior ofrecería evidencia débil sobre el incidente original.

La sincronización a RDE no pasa los gates de Cloud Manager. Tras la prueba, el cambio debe seguir la pipeline normal hacia Development. RDE sirve para desarrollo, análisis de errores y pruebas funcionales acotadas; no equivale a stage ni producción. Un reset elimina el código y contenido actuales, por lo que se coordina si el ambiente es compartido. Esta sesión no hace reset ni despliegue. RDE — Adobe.

Comandos de la slide 08

Como referencia, con AIO CLI, el plugin RDE, permisos y un ambiente disponible, la secuencia sería:

aio login
aio aem:rde:setup
aio aem:rde:status
aio aem:rde:install <artifact.zip>
aio aem:rde:history

<artifact.zip> representa un paquete construido para el proyecto. setup elige el RDE; status comprueba disponibilidad y despliegues; install sincroniza el artefacto; history muestra el historial. La instalación sin opción de servicio apunta a Author y Publish. Confirma que el RDE seleccionado sea el correcto antes de instalar. Los comandos no se ejecutaron para preparar la clase. 4. Conclusión defendible

En la ficha inventada, Publish devuelve 500; el log apunta a CatalogService; Developer Console muestra que su referencia CatalogClient no está disponible; el nodo base existe en Publish. La siguiente comprobación es averiguar por qué falta CatalogClient. Una corrección candidata se probaría en RDE y después por la pipeline normal.

Aún no se puede afirmar que faltó desplegar un bundle específico o que el problema quedó corregido. El proveedor puede estar ausente o existir sin activarse por configuración o dependencia. Inspeccionarlo distingue esas hipótesis.

Repaso con respuestas

  1. ¿Por qué abrir logs de Publish? El 500 observado pertenece a Publish; los logs de Author responderían otra pregunta.
  2. ¿Bundle ACTIVE implica componente activo? No; componente y referencias tienen su propio estado.
  3. ¿Qué demuestra ver jcr:content? Presencia visible del nodo base, no render ni acceso universal.
  4. ¿Qué sigue tras CatalogClient → MISSING? Revisar proveedor, bundle, registro y configuración de activación.
  5. ¿Por qué no basta un 200 en RDE? Primero hay que reproducir el 500; además RDE no pasa los gates de la pipeline.
