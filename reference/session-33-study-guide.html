Diagnosticar la caché de Dispatcher

Reglas, invalidación, stat files, TTL y parámetros de URL con una secuencia observable.

  • Núcleo de 30 minutos · ampliable a 60
  • Descargar Markdown completo
  • Slides en inglés
Objetivo: ante una página correcta en Publish pero antigua en Dispatcher, demostrar con la misma petición un miss, un hit y una respuesta actualizada tras publicar un cambio controlado. Entregar Host, URL, versión visible y evidencia de logs o archivos para cada paso.

Para 60 minutos, añade 20 de ejecución local y 10 de discusión. Prepara Author, Publish, Docker y Dispatcher Tools antes de la clase. Sin entorno local, analiza la traza simulada y pide la siguiente prueba. La sesión 32 ubicó la petición; la 34 separará navegador y CDN. Caché Cloud — Adobe.

1. La misma petición en dos límites

Comprueba primero la versión en Publish. Después usa el mismo método GET, Host y path por Dispatcher. No cambies query string ni añadas un parámetro de “cache busting”: /ignoreUrlParams puede ignorarlo o dejar la respuesta fuera de caché. Registra hora, status y un marcador visible en el HTML, además del log de Dispatcher y el request log de Publish. Dos HTTP 200 iguales no prueban un hit; una decisión de caché correlacionada con la ausencia de nueva GET en Publish sí lo sostiene. Parámetros — Adobe · Logs — Adobe.

2. Qué puede entrar y qué puede quedar obsoleto

AjustePreguntaEvidencia
/cache/rules¿Puede almacenarse el path?Regla efectiva y archivo bajo /docroot.
/cache/invalidate¿Qué archivo queda obsoleto tras actualizar?Regla, flush y tiempos del archivo y .stat.
/statfileslevel¿Qué región del árbol se invalida?Nivel y timestamps locales.
/enableTTL¿Expira por tiempo?Headers, archivo .ttl y nueva GET a Publish.
/ignoreUrlParams¿Se reutiliza la misma respuesta para parámetros distintos?Regla por nombre y versión servida.

/filter permite o rechaza la petición; no decide por sí mismo si se guarda. Además de /cache/rules, revisa método GET/HEAD, extensión, query, autenticación y headers de respuesta. Por defecto, una petición con Authorization, cookie authorization o login-token no se cachea con /allowAuthorized "0". Usa una página pública .html para este laboratorio. Elegibilidad — Adobe · Autenticación — Adobe.

Una actualización elimina directamente el archivo correspondiente y puede marcar otros documentos como obsoletos tocando .stat. Esos documentos pueden seguir en disco hasta la siguiente petición. Dispatcher compara tiempos y consulta Publish si el archivo cacheado es anterior al .stat pertinente. /statfileslevel fija el alcance: revisa el path y docroot antes de modificarlo. Stat files — Adobe · Invalidación Cloud — Adobe.

Con /enableTTL "1", Dispatcher usa headers de expiración del backend para volver a solicitar un archivo. En las versiones actuales, la invalidación estándar puede actualizarlo antes de que venza el TTL. Ese ajuste de Dispatcher no define por sí solo la política del navegador o CDN. TTL — Adobe.

En /ignoreUrlParams, allow significa ignorar el parámetro al decidir la caché; deny significa no ignorarlo y dejar esa petición fuera de caché de Dispatcher. Si el parámetro cambia el HTML, ignorarlo podría servir la variante equivocada. La clave del CDN puede tratar la query de otro modo. Semántica de parámetros — Adobe · Caché CDN — Adobe.

3. Caso guiado: A, A, B, B

Traza didáctica simulada; no es una ejecución registrada. La página pública /content/site/en/cache-lab.html muestra Version A. La farm permite almacenarla y el flush está configurado para ese path.

PasoPublishDispatcherPrueba
Primera GETAANueva GET a Publish y archivo cacheado: miss.
Misma GETAASin nueva GET a Publish: hit.
Cambiar A por B y publicarBA antes de nueva GETPublicación, flush y cambio de .stat o archivo eliminado.
Misma GET tras publicarBBNueva GET a Publish: refresh.
Misma GET de nuevoBBSin nueva GET a Publish: hit.

Si Dispatcher conserva A, comprueba que Publish tenga B, la farm elegida por Host, el flush recibido, el path de invalidación y la elegibilidad por /invalidate. Si sólo cambió un fragmento o asset, publicar esa dependencia no demuestra que se invalidó el HTML que la consume. Invalidación — Adobe.

4. Demo local con Dispatcher Tools

Prepara Docker, Author localhost:4502, Publish localhost:4503, proyecto instalado y Dispatcher Tools. Usa Host y path reales de tu proyecto. Ejecuta desde la carpeta extraída de Dispatcher Tools en macOS/Linux; en Windows consulta la guía local. Dispatcher Tools — Adobe.

DISP_LOG_LEVEL=Debug ./bin/docker_run_hot_reload.sh /ruta/al/proyecto/dispatcher/src host.docker.internal:4503 8080

Sustituye el Host y path ficticios. Usa una URL de prueba aún no solicitada a este Dispatcher si buscas observar el primer miss. Mantén la misma URL en las repeticiones. curl -i muestra headers y marcador del cuerpo.

curl -i 'http://localhost:4503/content/site/en/cache-lab.html'
curl -i -H 'Host: www.example.test' 'http://localhost:8080/content/site/en/cache-lab.html'
curl -i -H 'Host: www.example.test' 'http://localhost:8080/content/site/en/cache-lab.html'
  1. Registra A, hora, status, URL, Host y logs de cada GET. Si la primera es hit, localiza la entrada existente o usa otra página de prueba.
  2. En Author cambia el marcador a B, publica la misma página y confirma B directamente en Publish.
  3. Busca flush y modificación de .stat o eliminación del archivo. Repite dos GET idénticas por Dispatcher y comprueba cuándo llega una nueva GET a Publish.
  4. Si no se actualiza, conserva la evidencia y revisa farm, reglas, path y conexión de flush. Cambia una sola condición en una copia local para probar la hipótesis; no limpies globalmente la caché.
EvidenciaRegistro
EntradaGET, Host, path, hora y query invariable.
ContenidoMarcador A o B en Publish y Dispatcher.
CachéRegla, archivo o línea de hit/miss/refresh y GET en Publish.

ConclusiónPrimer paso distinto y causa sostenida por evidencia.

Resultados esperados, no ejecución registrada. La secuencia depende de la farm y del flush local; una observación distinta es material para el diagnóstico. Las herramientas locales no reproducen el CDN de Cloud.

5. Decisión al cierre

Primera evidencia distintaContinuación
Publish aún muestra ASesión 31: publicación, path y dependencias.
Publish B; Dispatcher no guardó A/cache/rules, método, extensión, query, auth y headers.
Publish B; Dispatcher aún muestra AFlush, Host/farm, path, /invalidate, .stat, TTL y logs.
Dispatcher B; URL pública externa ASesión 34: navegador y CDN.

Repaso con respuestas

  1. ¿/cache/rules o /invalidate? La primera decide qué entra; la segunda qué archivos quedan obsoletos.
  2. ¿Dos HTTP 200 prueban hit? No; comprueba la decisión de Dispatcher y que Publish no recibió otra GET.
  3. ¿Qué hace .stat? Su timestamp marca contenido anterior como obsoleto.
  4. ¿TTL impide invalidar antes? No en las versiones actuales documentadas.
  5. ¿Qué significa allow en /ignoreUrlParams? Ignorar el parámetro para la decisión de caché.
  6. ¿Borrar toda la caché prueba la causa? No; puede quitar el síntoma sin explicar el fallo.
