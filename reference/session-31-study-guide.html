1. Cuatro puntos de control para un path

Author: acción, destino y paths seleccionados
  → SCD: solicitud aceptada y encolada
  → Publish: contenido importado
  → Comprobación: el path sirve la versión esperada

En AEM as a Cloud Service, Sling Content Distribution (SCD) mueve contenido mediante un servicio externo al runtime. El agente publish está habilitado por defecto; preview dirige al destino Preview cuando está configurado. Una acción enviada no demuestra importación completada. Replicación Cloud — Adobe.

Quick Publish selecciona páginas de forma superficial y puede añadir referencias no publicadas. Manage Publication permite revisar hijas, referencias, acción, destino y programación. Anota los paths de página y assets incluidos: una referencia compartida puede servir a otras páginas. Alcance en Sites — Adobe.

2. Dos colas, dos significados

En Cloud abre Tools → Deployment → Distribution → publish. Las colas están consolidadas; no hay una por cada pod. Colas SCD — Adobe.

ColaQué significa que el elemento salgaSi sigue pendiente
persistedEl cambio quedó almacenado de forma duradera en Publish; los pods convergen con el tiempo.Inspecciona el path, Items Pending, Last Item Processed y Logs.
fully publishedEl cambio está activo en todos los pods y terminó la invalidación asociada para los paths afectados.Inspecciona path pendiente, último elemento y Logs.

La pestaña Status muestra salud, Items Pending y Last Item Processed; Test Connection y Logs añaden evidencia. Si una cola está roja, registra el primer path y el error. Esta clase sólo inspecciona: vaciar la cola puede descartar cambios ajenos. Monitorización — Adobe.

3. ReplicationStatus no es una prueba física

Para un recurso se puede adaptar a ReplicationStatus; para muchos, ReplicationStatusProvider.getBatchReplicationStatus(...). Fragmento de lectura diagnóstica, sin servlet ni nueva acción:

Resource page = resolver.getResource(pagePath);
ReplicationStatus status = page == null ? null : page.adaptTo(ReplicationStatus.class);
ReplicationStatus live = status == null ? null : status.getStatusForAgent("publish");
if (live != null) {
    LOG.info("action={}, pending={}, delivered={}",
        live.getLastReplicationAction(), live.isPending(), live.isDelivered());
}
MétodoLectura correcta
isActivated()La última acción fue Activate; no afirma que ya se importó.
isPending()La última acción sigue en alguna cola.
isDelivered()Se calcula con logs de replicación; no comprueba presencia física del contenido.
getStatusForAgent("preview")Estado del destino Preview, separado del estado de Publish.

Una acción sólo a Preview puede dejar sin cambio el estado general, porque éste se actualiza cuando participa un agente habilitado por defecto. Consulta el agente concreto y comprueba su destino. ReplicationStatus — Javadoc · Estado por agente — Adobe.

4. Caso guiado: path pendiente en Cloud

Evidencia didáctica simulada, no un incidente real. A las 10:04 se solicitó Activate a publish para /content/wknd/us/en/training-publication junto con /content/dam/wknd/training/cover.png.

SeñalInterpretación
Última acción Activate; isPending() = trueLa acción sigue pendiente; isActivated() no resuelve el caso.
persisted: 1 elemento, path del assetBusca ese path y el primer error en Logs.
fully published: 1 elementoLa confirmación final aún no termina.
Publish muestra la versión anteriorEs coherente con la distribución pendiente; todavía no atribuyas nada a Dispatcher.

Respuesta del ejercicio: inspecciona el elemento pendiente del asset, registra path y error, y observa Last Item Processed. Una referencia que no se importa puede detener trabajo posterior. No borres la cola para probar. Si ambas colas quedan sanas y Publish muestra la versión correcta, la publicación quedó demostrada y una discrepancia en la URL pública pasa a la sesión 32. Diagnóstico de colas — Adobe.

5. Demo local: misma pregunta, otro transporte

Usa Author desechable http://localhost:4502 y Publish desechable http://localhost:4503 con el mismo proyecto instalado. Sigue la guía oficial del SDK para conectar el agente local a /bin/receive. No presentes su cola clásica como las dos colas SCD de Cloud.

  1. Anota los paths reales de una página de prueba y un asset propio. Inserta el asset en la página, escribe Versión A, publícala y verifica página y asset en Publish :4503.
  2. Cambia a Versión B en Author sin publicar. Compara fecha de modificación y publicación en Sites; Publish debe seguir mostrando Versión A.
  3. Usa Manage Publication → Publish → Now. Revisa y anota página, asset, destino y hora. Si el asset no se detecta como referencia, comprueba el enlace y añádelo de forma explícita.
  4. Inspecciona estado y agente local en Author. Abre los paths exactos de página y asset en Publish :4503; comprueba Versión B.
  5. Si queda tiempo, despublica sólo la página de prueba y verifica que sigue en Author; conserva el asset compartido.
Evidencia mínimaRegistro
Acción y destinoActivate → publish, no preview.
AlcancePaths completos de página y asset.
AuthorHora, última acción y estado pendiente.
TransporteAgente local; en Cloud, agente SCD y dos colas.
PublishURLs exactas, versión visible y asset.

Resultados esperados, no ejecución registrada en este repositorio. Si Publish :4503 sirve la versión correcta, la publicación local funcionó. Esta demo no demuestra el comportamiento de las colas SCD Cloud.

6. Decidir dónde continúa el diagnóstico

EvidenciaSiguiente paso
No hay acción para el path, o el destino era PreviewRevisa selección, destino y estado por agente.
isPending() y path en persistedInspecciona primer elemento pendiente y Logs.
persisted despejada; fully published pendienteObserva convergencia y Logs; evita republicar en bucle.
Colas sanas, asset ausente en PublishVerifica su path y estado individual.
Página y asset correctos en Publish, URL pública distintaLleva la petición a Apache y Dispatcher en la sesión 32.

Repaso con respuestas

  1. ¿Qué demuestra isActivated()? Sólo que la última acción fue Activate.
  2. ¿Qué diferencia hay entre las dos colas? Almacenamiento duradero frente a publicación completa en todos los pods.
  3. ¿Por qué importa el primer path pendiente? Puede ser el recurso que bloquea trabajo posterior.
  4. ¿Cómo lees Preview separado de Publish? Con getStatusForAgent(...) y la URL del destino.
  5. ¿Qué no prueba el SDK local? El comportamiento de las colas SCD Cloud.
  6. Si Publish es correcto y la URL pública no, ¿qué sigue? Sesión 32: Apache y Dispatcher.
