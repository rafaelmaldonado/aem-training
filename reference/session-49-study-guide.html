Medir y corregir un cuello de botella en AEM

Una línea base, una hipótesis y un cambio cuya mejora se pueda comprobar.

  • 30 minutos
  • Abrir slides
  • Guía Markdown completa
Objetivo observable: medir cinco veces la misma página de Publish, localizar el retraso, cambiar sólo el asset de la imagen LCP y repetir la medición con igual protocolo. Las cifras que aparecen en el material son simuladas.

Conceptos clave

Línea base es la medición previa con condiciones registradas; presupuesto, el límite acordado antes del cambio. TTFB mide hasta el primer byte del HTML e incluye red y espera del servidor. LCP marca cuándo aparece el elemento de contenido más grande en el viewport. Una reducción del tamaño de la imagen sólo demuestra mejora de LCP si se observa en las nuevas mediciones. La guía Markdown explica las etapas y el registro completo.

El caso y su presupuesto

Usa una página desechable guide-49-lab con Core Image visible al inicio. Prepara una foto pesada y otra visualmente equivalente más ligera. En Publish local, comprueba que la foto pesada es el elemento LCP y que su descarga contribuye al retraso. El defecto es preparado para la práctica; no se atribuye al Core Image por defecto.

CondiciónAcuerdo didáctico
EscenarioMisma URL, 390 × 844 CSS px, mismo perfil de red y CPU, primera visita sin caché de navegador.
MuestrasUna corrida de calentamiento y cinco mediciones antes y después; comparar medianas y variación.
PresupuestoMediana LCP ≤ 3,0 s; imagen LCP ≤ 300 kB transferidos; calidad y alt conservados.
CambioUn solo asset en Core Image. No cambiar texto, posición, URL ni configuración de caché.

Estos límites pertenecen al laboratorio. No son un estándar universal ni un resultado ya obtenido.

Separar capas antes de intervenir

ObservaciónPrimera comprobación
HTML tardaNetwork, caché y tiempo en request.log; revisar consultas sólo con evidencia.
Miss lento, hit rápidoElegibilidad e invalidación del Dispatcher, si existe en el entorno.
Imagen LCP inicia tardeDescubrimiento, prioridad, loading y clientlibs.
Imagen LCP descarga demasiados bytesRecurso, formato, dimensiones y tamaño transferido reales.
Imagen termina pronto, pinta tardeTareas principales, estilos y scripts en la traza.

El SDK local puede carecer de CDN y Dispatcher; registra esas capas como no observadas. No interpretes TTFB como tiempo exclusivo de AEM. El servicio de imágenes web optimizadas de AEM Cloud tampoco se valida en localhost, donde Core Image puede usar Adaptive Image Servlet.

Práctica local · Author SDK y Publish

  1. Prepara la página y publica la versión inicial. Fija URL, viewport, red, CPU y caché; registra la versión de Chrome y el estado HTTP.
  2. Haz una corrida de calentamiento y cinco mediciones. Guarda cada LCP y su mediana. En Network/Performance identifica el elemento LCP, TTFB, recurso de imagen, bytes, duración y clientlibs relevantes.
  3. Si la imagen no es LCP o su descarga no es material, registra el hallazgo y sigue la capa indicada por la evidencia. En el caso preparado, confirma ambos puntos antes de corregir.
  4. En Author sustituye sólo el asset del Core Image por la variante optimizada. Publica y verifica en Publish la URL del recurso, tipo, dimensiones, bytes, nitidez, encuadre y alt.
  5. Repite una corrida de calentamiento y cinco mediciones bajo las mismas condiciones. Compara medianas y rangos; verifica si el elemento LCP cambió.
  6. Acepta el cambio si cumple el presupuesto y conserva calidad. Si sólo bajan los bytes, inspecciona la siguiente etapa en la traza; si la diferencia es pequeña frente a la variación, mide de nuevo.

Un ejemplo simulado sería 1,6 MB → 260 kB y mediana LCP 3,6 → 2,7 s, con TTFB similar y calidad conservada. Sólo una ejecución real permite afirmar ese resultado para la página de práctica. La guía Markdown incluye tabla de registro, limpieza, diagnóstico y respuestas.

Repaso con respuestas

  1. ¿TTFB alto prueba una consulta lenta? No; separa red, caché y Publish.
  2. ¿Menos bytes garantizan mejor LCP? No; mide también carga y render.
  3. ¿El SDK prueba la entrega web optimizada de AEM Cloud? No; verifica esa función en Cloud.
  4. ¿Cuándo se acepta el cambio? Cuando mediciones comparables cumplen el presupuesto y mantienen calidad y significado.
