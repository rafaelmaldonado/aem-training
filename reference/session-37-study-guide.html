Leer un fallo de pipeline

Ubicar el primer error accionable, delimitar el ambiente afectado y elegir una recuperación compatible.

1. Leer la ejecución por etapas

En una pipeline productiva full-stack, el recorrido puede incluir validación, build y pruebas unitarias, análisis de código, creación de imágenes, despliegue a stage, pruebas en stage, aprobación y despliegue a producción. Los slides simplifican esta ruta; la lista exacta depende del tipo y configuración. En AEM as a Cloud Service, las reglas de seguridad de código se evalúan dentro del análisis de calidad, sin una etapa separada de security testing. Una pipeline de calidad no despliega. Desplegar código — Adobe · Code quality — Adobe.

Lee SHA y origen → primera etapa con fallo o pausa → primera causa en el log → etapas no alcanzadas → ambiente actualizado. Un resumen rojo no basta para afirmar que producción recibió el cambio.

FronteraEvidencia útilConclusión limitada
BuildPrimer error de compilación, dependencia o paquete.No hay artefacto válido de ese run.
Calidad y seguridadRegla, componente, severidad y estado del gate.Pausa o fallo no prueba despliegue.
PruebasPetición, esperado, obtenido y ambiente.Se conoce el comportamiento fallido allí.
DespliegueArtefacto, ambiente, paso y error.Se delimita qué destino alcanzó.

Cobertura local con JaCoCo

Ejemplo opcional para el instructor: en el módulo Java core de un proyecto AEM Maven, declarar en core/pom.xml el plugin JaCoCo:

<plugin>
  <groupId>org.jacoco</groupId>
  <artifactId>jacoco-maven-plugin</artifactId>
  <version>0.8.15</version>
</plugin>

Desde core/, con dependencias disponibles, prepararlo y ejecutar las pruebas en una sola invocación:

mvn jacoco:prepare-agent test jacoco:report

El reporte se abre en core/target/site/jacoco/index.html desde la raíz. Muestra líneas y ramas ejecutadas; los porcentajes de la lámina 5 son ficticios. El resultado local no reproduce el gate completo de Cloud Manager ni prueba por sí solo que las aserciones sean correctas. Si Surefire ya define argLine, debe conservar el argumento de JaCoCo. 2. Ejemplo: falla el build

Log ficticio:

[ERROR] Could not resolve com.example:site-core:jar:1.4.2
[ERROR] Failed to execute goal
Tests skipped

La dependencia que no se pudo resolver es la primera causa investigable. “Failed to execute goal” resume la caída y “Tests skipped” es una consecuencia. Se revisan coordenadas, versión y repositorio declarados para ese commit. No hay evidencia de entrega a stage ni de fallo de las pruebas.

3. Ejemplo: falla una prueba en stage

Run ficticio #43, distinto del #42 de la sesión 36: build y code quality pasan; el despliegue a stage termina; una prueba funcional solicita GET /content/site/en.html y obtiene 404 en vez de 200. Producción no se inicia.

El primer fallo accionable es la aserción en stage. El 404 aún no identifica la causa: se revisarían URL y Host de la prueba, contenido disponible y publicado, artefacto del SHA y respuesta/logs de la capa que devolvió el error. La corrección depende de esa comprobación. No se describe como fallo de build ni como despliegue productivo.

4. Código y contenido durante la actualización

Un despliegue gradual puede mantener código antiguo y nuevo activos a la vez mientras comparten contenido mutable. Al volver al código anterior, los cambios de contenido mutable no se deshacen automáticamente. Despliegue gradual — Adobe.

Ejemplo didáctico: una tarjeta pasa de leer old_field a new_field. La versión A acepta ambos campos; se comprueba con contenido antiguo y nuevo. Después, la versión B empieza a escribir new_field y sigue leyendo old_field. La limpieza del lector antiguo se reserva hasta comprobar que ya no lo necesita el contenido existente ni una eventual reversión. Cloud Manager no migra estos campos por sí mismo.

5. Recuperar según la frontera

Situación ilustrativaDecisión
Antes de producir artefactoCorregir build o gate y validar una nueva ejecución.
Prueba fallida en stageInspeccionar stage y corregir la causa verificada antes de producción.
Durante despliegueConfirmar paso, ambiente y estado real antes de reintentar.
Después de producciónContener impacto; valorar restauración del código disponible y comprobar por separado el contenido mutable.

Adobe documenta Restore previous code deployed para volver al último build exitoso cuando se cumplen sus condiciones. Restaura código, no contenido mutable; esta guía no ejecuta la operación. Restaurar código anterior — Adobe.

Método de lectura: “El run del SHA indicado llegó hasta [etapa/ambiente]; el primer error explicativo es [dato]; [etapas posteriores] no se completaron; la siguiente acción es [corrección o inspección verificable]”.
