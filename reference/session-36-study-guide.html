Elegir el flujo de entrega

Relacionar el cambio con su commit, pipeline, artefacto y ambiente de destino.

1. Las coordenadas de una entrega

Cloud Manager relaciona programa, ambientes, repositorios y pipelines. Para una ejecución concreta, anota repositorio, rama, ruta de código cuando aplique, SHA del commit, artefacto y destino. Una ejecución verde no identifica por sí sola qué cambio se construyó. Los repositorios pueden estar administrados por Adobe o ser externos compatibles. Repositorios — Adobe.

Separa destino y propósito de contenido entregado. Una pipeline no productiva de despliegue puede apuntar a desarrollo; la productiva estándar entrega primero a stage y después a producción, con sus controles y aprobación. Una pipeline de calidad analiza sin desplegar. Comprueba qué etapa alcanzó la ejecución. Pipeline productiva — Adobe · Ambientes — Adobe.

2. Elegir por el cambio real

CambioPipeline habitualComprobación
Java, Sling Models, OSGi, Repo Init, paquetes AEM o clientlibs empaquetadasFull-stackEl módulo y sus dependencias están en la rama construida.
Tema o aplicación estática que el sitio consume por separadoFront-endEl sitio usa ese tema; HTML/JSON conserva compatibilidad.
Vhost, rewrite, filtros o caché de Apache/DispatcherWeb tier config, si existe para ese ambienteQuién entrega Dispatcher y cuál es el code location.
Reglas CDN, log forwarding o mantenimiento soportadoConfigTipo admitido y archivo dentro de la ruta seleccionada.

Full-stack entrega backend y frontend empaquetado como clientlibs. Puede incluir Dispatcher; si el ambiente tiene web tier config pipeline, el full-stack ignora los archivos Dispatcher allí. Front-end entrega un build estático separado y requiere que el sitio lo use. La pipeline config no sustituye la entrega de .cfg.json OSGi. El SHA y el run son ficticios. En la discusión, indica qué dato permitiría verificar el commit, el artefacto y el destino si se tuviera acceso. Desplegar código, publicar contenido y refrescar cachés son observaciones distintas.

Caso guiado: verde en la rama equivocada

Traza simulada; no es un run real de Cloud Manager. El commit c36b2 corrige un vhost para www.example.test en feature/host-fix. main todavía termina en a36f1. La pipeline web-tier-dev lee main, ruta dispatcher/, y entrega a dev. Su run #42 termina en verde, pero la petición sigue fallando.

Diagnóstico: el tipo de pipeline es adecuado, pero el run no contiene el arreglo. La recomendación sería integrar el commit según el flujo del equipo antes de una futura ejecución; entonces harían falta el nuevo SHA, run y resultado en dev. Si el nuevo run incluye el arreglo y llegó a dev, inspecciona el artefacto y la respuesta en la capa web. Un run de code quality verde tampoco prueba despliegue.

Análisis guiado sin entorno

El instructor muestra la traza simulada anterior y pausa antes de revelar cada respuesta. No se abren Cloud Manager, Git ni una terminal.

  1. Muestra dispatcher/site.vhost. Pregunta quién entrega ese archivo. Respuesta: web tier config si es dueña del ambiente; en otro caso, se comprueba la opción Dispatcher del full-stack.
  2. Muestra feature/host-fix → c36b2 y main → a36f1. Pregunta si un run de main puede contener el arreglo. Respuesta: no, según la ficha.
  3. Muestra web-tier-dev, run #42, verde y destino dev. Pregunta qué prueba ese estado. Respuesta: terminó esa ejecución; no demuestra que incluyera c36b2 ni que producción recibiera cambios.
  4. Pide una conclusión de una frase: «La pipeline corresponde al archivo, pero el run #42 tomó main en a36f1; por eso no contiene c36b2».

Variante para discusión: si el run usara c36b2, ¿qué faltaría? Artefacto generado, etapa completada y respuesta en el destino. La sesión 37 tratará fallos de esas etapas. Todos los datos son didácticos.

Preguntas de aplicación

Discute cuatro situaciones hipotéticas: identifica la pipeline probable y qué dato confirmaría origen y destino. No se ejecuta nada.

  1. Sling Model y OSGi versionado: full-stack; comprobar paquete y servicio.
  2. CSS de tema entregado por front-end pipeline: front-end; comprobar build y versión del tema. Una clientlib AEM empaquetada sigue full-stack.
  3. Rewrite de Dispatcher: web tier si existe para el ambiente; si no, comprobar la opción del full-stack. En un entorno real harían falta status y Location con el Host correcto.
  4. Reenvío de logs admitido: config; identificar archivo, tipo admitido, pipeline y ambiente destino en la ficha suministrada. No afirmar que el cambio está desplegado ni usar config para .cfg.json OSGi.

Repaso con respuestas

  1. ¿Verde significa que mi commit llegó a producción? No; comprueba SHA, tipo y etapa.
  2. ¿Code quality despliega? No; sólo analiza.
  3. ¿Dónde va una clientlib del proyecto? En full-stack, salvo que exista una entrega estática separada y usada por el sitio.
  4. ¿Quién entrega Dispatcher cuando hay web tier config? Esa pipeline; full-stack lo ignora en ese ambiente.
  5. ¿Publicar una página es desplegar código? No; son operaciones distintas.
