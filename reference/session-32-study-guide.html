Seguir una petición por Apache y Dispatcher

Host, vhost, farm, rewrite, filtro, headers y primera capa que responde.

1. Ruta y evidencia de una petición

Navegador → CDN → Apache (vhost y rewrites) → Dispatcher (farm y filtro) → Publish

Registra método, URL, Host, hora, status y headers antes de seguir redirecciones. No uses curl -L al capturar la primera respuesta. El CDN puede responder antes de Apache. Compara logs de Apache con la misma hora y Host; la ausencia de una línea sólo es un indicio si la correlación es fiable. Tráfico CDN — Adobe · Logs Cloud — Adobe.

ServerName y ServerAlias participan en la elección del virtual host. Revisa el vhost habilitado y los rewrites incluidos. Dispatcher selecciona una farm mediante /virtualhosts; la farm aporta /filter y /renders. El mismo path con otro Host puede recorrer otra configuración. Configurar Dispatcher — Adobe · Validar y depurar — Adobe.

2. Rewrite, redirect, filtros y headers

MecanismoSeñalPrueba
Rewrite internoLa URL del navegador permanece; cambia el path interno.Compara URI original, regla y path recibido en destino.
Redirect externoRespuesta 3xx con Location; el navegador hace otra petición.Captura ambos sin seguir automáticamente el primero.
Filtro de Dispatcher/filter permite o rechaza antes del renderer. Un rechazo devuelve normalmente 404.Busca la decisión en el log y comprueba si Publish recibió la petición.
Header de peticiónHost afecta selección; /clientheaders determina headers enviados al renderer.Compara entrada, configuración y destino.

RewriteRule con [R] genera un redirect externo. Una sustitución interna conserva la URL del navegador. Apache también ofrece Redirect y RedirectMatch para casos simples. Un redirect también puede originarse en el CDN. mod_rewrite — Apache · Flags — Apache · CDN — Adobe.

El filtro puede comparar método, URL, query, path, selectors, extensión y suffix. Adobe documenta 404 para una petición rechazada por /filter. Un 403 no demuestra una denegación de ese filtro; un 404 tampoco prueba ausencia de contenido. Ubica la capa con logs. Filtros — Adobe.

/clientheaders define qué headers del cliente llegan al renderer. Los headers de respuesta, incluidos Location y Cache-Control, se inspeccionan por separado y pueden cambiar en Apache o CDN. clientheaders — Adobe.

3. Caso guiado: tres respuestas

Evidencia didáctica simulada; no es una ejecución registrada. El contenido de /content/site/en/adventures.html ya se comprobó en Publish. Usa el Host ficticio www.example.test.

ObservaciónPrimera lecturaPrueba siguiente
/old devuelve 302 y Location: /new; Publish no recibe /old.Respondió una capa anterior a Publish.Correlaciona log de Apache o CDN y regla; consulta /new después.
Una petición devuelve 404; Dispatcher registra rechazo de /filter; Publish no la recibe.Corte en la farm o filtro seleccionado.Identifica Host, farm y regla exacta.
/adventures devuelve 404; Dispatcher envía un path y Publish registra 404 para él.Corte en path resuelto o recurso destino.Compara rewrite efectivo y path publicado.

Respuesta: ningún status por sí solo resuelve el caso. Se necesita Location, presencia en access logs y decisión de Dispatcher/Publish. Un 403 se investiga de igual manera, sin asignarlo automáticamente a ACL o filtro. Logging — Adobe.

4. Demo local con Dispatcher Tools

Prepara Docker, Publish del SDK en localhost:4503, el proyecto instalado y Dispatcher Tools del SDK. Usa un Host y una página de prueba reales de tu proyecto. Ejecuta desde la carpeta extraída de Dispatcher Tools. Adobe documenta el script de hot reload para macOS/Linux y bin\docker_run para Windows. Dispatcher Tools — Adobe.

./bin/docker_run_hot_reload.sh /ruta/al/proyecto/dispatcher/src host.docker.internal:4503 8080

En otra terminal, sustituye los valores ficticios por Host y path de tu proyecto. Captura la primera respuesta sin -L y compara con Publish directo.

curl -i -H 'Host: www.example.test' 'http://localhost:8080/content/site/en/adventures.html'
curl -i 'http://localhost:4503/content/site/en/adventures.html'
  1. Registra status, Location y path. Si hay 3xx, consulta el destino en una petición nueva.
  2. Repite con tu Host configurado y con otro Host; observa vhost y farm.
  3. Revisa stdout de Dispatcher Tools. Si hace falta, arranca con DISP_LOG_LEVEL=Debug REWRITE_LOG_LEVEL=Debug. Correlaciona con logs de Publish.
  4. Cambia una sola regla en una copia local, deja que hot reload la valide y repite la misma petición. Guarda antes y después; no despliegues la regla de ejercicio.

5. Decidir dónde continúa el diagnóstico

Primera evidencia distintaContinuación
CDN responde y Apache no recibe la peticiónReglas y logs CDN, Host y hora.
Apache recibe Host incorrecto o emite 3xxVhost, alias y redirects/rewrites.
Dispatcher elige otra farm o rechaza/virtualhosts, /filter y log.
Publish recibe otro path o responde 403/404Rewrite efectivo, recurso y logs de Publish.
Publish correcto, URL pública viejaSesión 33: caché e invalidación.

Repaso con respuestas

  1. ¿Rewrite o redirect? El redirect devuelve 3xx y Location; el rewrite conserva la URL del navegador.
  2. ¿Por qué registrar Host? Afecta vhost y farm.
  3. ¿Qué devuelve normalmente un rechazo de filtro? 404; confirma con log.
  4. ¿Un 403 prueba ACL? No; primero identifica la capa.
  5. ¿Para qué sirve /clientheaders? Define headers del cliente que pasan al renderer.
  6. ¿Qué sigue si Publish es correcto pero la URL pública está vieja? Caché en la sesión 33.
