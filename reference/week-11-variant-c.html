Semana 11 · Variante C

Lista acotada, entrega local y pruebas

Una Core List filtrada por tag, una consulta de diagnóstico con límite explícito, evidencia de Publish/Dispatcher y una prueba de navegador sobre el resultado visible.

  • Author y Publish locales
  • Dispatcher Tools si están disponibles
  • Consigna y criterios
Resultado que vas a mostrar: Forest y River aparecen; City ride, Visitor notes y Outside trail quedan fuera. Guarda el plan y la medición de la consulta, una comparación HTTP antes/después, un test negativo y una observación de calidad repetida.

1. Preparar página y datos

  1. Crea Weekend Guides con la editable template y los Core Components comunes: Title, Image con alt útil, Text introductorio y Container. Permite List o su proxy en la policy del contenedor. Usa la URL real de tu sitio.
  2. Reutiliza el conjunto de la sesión 26: bajo training-search crea 01 Forest trail y 02 River trail con tag training:activity/hiking; 03 City ride con Cycling; 04 Visitor notes sin tag; y 05 Outside trail con Hiking pero fuera de esa raíz. Ajusta el prefijo /content/wknd/us/en a tu sitio.
  3. Inserta el Core List Component en el área de guías. En su diálogo elige Build list using → Tags, Parent page → training-search, Tags → Hiking, Match → any, Order by → Title, ascendente, Max Items → 2 e ID → week11-guide-list. Activa enlaces de los items. No dejes Max Items vacío: eso permite devolver todos.
  4. En Preview confirma que los dos incluidos aparecen y los otros tres no. El componente existente ya resuelve y representa la lista; la práctica no necesita Java propio para ese comportamiento. Si tu baseline no ofrece la opción Tags, primero revisa el proxy y la policy de List antes de crear otro componente.

2. Código de la consulta diagnóstica

En el QueryBuilder Debugger local (http://localhost:4502/libs/cq/search/content/querydebug.html) pega estos predicados; sustituye sólo la raíz si tu sitio difiere. Sirven para comprobar el contrato de selección de la lista. El Core List puede construir internamente otra consulta, por lo que este plan no prueba por sí solo el coste interno del componente.

path=/content/wknd/us/en/training-search
type=cq:Page
property=jcr:content/cq:tags
property.value=training:activity/hiking
orderby=@jcr:content/jcr:title
orderby.sort=asc
p.limit=2
p.offset=0
p.guessTotal=true

El archivo querybuilder.properties tiene el mismo ejemplo. En CRXDE Lite, Tools → Query, puedes contrastar esta SQL2 con Limit 2 / Offset 0 de la herramienta; JCR-SQL2 no usa un LIMIT 2 SQL genérico:

SELECT * FROM [cq:Page] AS page
WHERE ISDESCENDANTNODE(page, '/content/wknd/us/en/training-search')
AND page.[jcr:content/cq:tags] = 'training:activity/hiking'
ORDER BY page.[jcr:content/jcr:title] ASC
  1. Ejecuta la consulta con la misma cuenta que inspecciona las páginas. Comprueba paths de Forest y River; con p.offset=2 no debe haber más hits. Si aparece City ride, revisa si también tiene Hiking; si aparece Outside trail, corrige la raíz.
  2. Abre Explain Query y Measure como en la sesión 27. Guarda el plan, índice elegido, número de nodos examinados y tiempo para este conjunto. Dos resultados no prueban una consulta barata. No declares que hace falta un índice nuevo sin observar el plan.
  3. Haz una prueba negativa visible: cambia temporalmente el tag de Forest a Cycling; la lista debe perder Forest. Restaura el tag y registra el resultado. Si existen páginas no legibles para el visitante, comprueba la lista con esa identidad: no eleves permisos mediante un service resolver para renderizar resultados.

3. Publish, Dispatcher y caché

Publica Weekend Guides, las dos páginas incluidas, sus assets, tags y otras dependencias que use la página. Confirma el HTML directamente en Publish antes de comparar Dispatcher. Si no tienes Publish/Dispatcher, usa la traza del instructor de las sesiones 32 y 33 y rotula cada dato como evidencia suministrada.

# Reemplaza Host y path; usa el mismo GET y la misma URL en cada repetición.
curl -i 'http://localhost:4503/content/<tu-sitio>/weekend-guides.html'
curl -i -H 'Host: www.example.test' 'http://localhost:8080/content/<tu-sitio>/weekend-guides.html'
curl -i -H 'Host: www.example.test' 'http://localhost:8080/content/<tu-sitio>/weekend-guides.html'

# Solicitud que la farm local debe permitir: la página pública anterior.
# Solicitud que una regla de /filter debe bloquear: elige una ruta de prueba
# realmente bloqueada en TU configuración y registra status y línea de log.
curl -i -H 'Host: www.example.test' 'http://localhost:8080/<ruta-bloqueada-real>'
  1. Con Docker y Dispatcher Tools del SDK, inicia la configuración de tu proyecto desde la carpeta extraída de Tools (ruta de ejemplo macOS/Linux): DISP_LOG_LEVEL=Debug ./bin/docker_run_hot_reload.sh /ruta/al/proyecto/dispatcher/src host.docker.internal:4503 8080. En Windows sigue la guía local.
  2. Identifica el vhost que recibe el Host elegido, la farm y la regla /filter que permite la página. Para una ruta bloqueada usa una regla existente de la configuración de prueba; no inventes una URL “prohibida” sin comprobar el log. Registra método, Host, path, status y regla.
  3. Primera GET a Dispatcher: busca la decisión de miss y la petición correspondiente en Publish. Segunda GET idéntica: busca hit y ausencia de otra GET a Publish. Dos códigos 200 no distinguen esas decisiones por sí solos.
  4. Haz un cambio controlado en el título de una página Guide, publica ese Guide y verifica primero el cambio en Publish. Repite la GET por Dispatcher. Si el HTML sigue antiguo, inspecciona el flush, /invalidate, .stat, Host y path antes de limpiar toda la caché.

Las pruebas locales no incluyen CDN. Si Publish y Dispatcher devuelven versiones distintas, la primera capa divergente observada es Dispatcher. Si ambos coinciden pero una URL pública real difiere, hace falta evidencia de la CDN y del navegador antes de atribuirla.

4. Tests que corresponden al código presente

Como esta solución usa Core List, no introduce una clase Java propia para la consulta ni JavaScript propio para la lista. Ejecuta los tests Java ya existentes del proyecto y revisa el reporte JaCoCo; selecciona una rama negativa relevante si vas a modificar código propio. Jest sólo aplica si hay una clientlib JavaScript personalizada que controle un comportamiento visible. No agregues Jest por obligación cuando sólo se usa Core List.

# En la raíz de TU proyecto AEM; ajusta el perfil JaCoCo si tu POM usa otro.
mvn -pl core test
mvn -pl core verify
# Abre core/target/site/jacoco/index.html si tu build genera ese reporte.

Si Cypress ya está configurado, guarda este spec como cypress/e2e/week-11-guides.cy.js. Usa los títulos exactos de las páginas publicadas y la URL real de Publish; prepara el contenido antes de ejecutar, sin credenciales de Author.

describe('Weekend Guides publicado', () => {
  it('muestra sólo las guías etiquetadas bajo la raíz', () => {
    const url = Cypress.env('publishPageUrl')
    expect(url, 'URL de Publish').to.be.a('string').and.not.be.empty
    cy.visit(url)
    cy.contains('h1', 'Weekend Guides').should('be.visible')
    cy.get('#week11-guide-list').within(() => {
      cy.contains('a', '01 Forest trail').should('be.visible')
      cy.contains('a', '02 River trail').should('be.visible')
      cy.contains('03 City ride').should('not.exist')
      cy.contains('04 Visitor notes').should('not.exist')
      cy.contains('05 Outside trail').should('not.exist')
    })
  })
})
export CYPRESS_publishPageUrl='http://localhost:4503/content/<tu-sitio>/weekend-guides.html'
npx cypress run --spec cypress/e2e/week-11-guides.cy.js

El selector usa el ID que asignaste en el diálogo del Core List; comprueba el HTML publicado si tu versión lo emite de otra forma. Su aserción negativa detecta una guía excluida dentro de la lista, no sólo un título de página. Si Cypress no está configurado, sigue la sesión 47 y registra mientras tanto la comprobación manual con la misma URL.

5. Calidad y evidencia final

  1. Con teclado, recorre los enlaces de la lista y observa foco visible. Comprueba el alt de la imagen informativa, el h1, el título de documento, canonical y robots de la URL publicada; la sesión 48 da el procedimiento.
  2. Elige un hallazgo medible: por ejemplo, una imagen LCP pesada. Fija URL, viewport, perfil de red/CPU y estado de caché; toma una línea base. Cambia sólo el asset por una variante de calidad suficiente y repite la medición con el mismo protocolo de la sesión 49. Si el problema real es la consulta, mide y corrige esa consulta en vez de tocar la imagen.
  3. Entrega URL, fixture/tag, plan y medida de consulta, respuesta de Publish/Dispatcher o traza suministrada, comando y resultado de tests, y antes/después de la corrección. Distingue lo observado de lo esperado.
