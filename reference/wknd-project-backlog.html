Eleven weekly practices · one developer per repository

Individual WKND practices.

One common, optional practice is introduced every Monday. Explore the supplied example or implement the extension in your own repository and local AEM SDK. Share progress before Friday if you want feedback; Friday is for recap and voluntary demos.

  • Introduced Monday
  • Optional feedback before Friday
  • Recap and demos Friday
Practice model: participation, submissions and demos are voluntary; there is no grade or required final defense. Each week has a supplied starting example, so earlier practices are not prerequisites. No shared deployment environment or Cloud Manager access is required. Cloud topics use public documentation and clearly identified supplied evidence; hands-on checks run locally.

Product scenario

The shared scenario is Weekend Guides, using either the public WKND tutorial repository or a project generated with AEM Project Archetype. The following are possible capabilities across the course, not prerequisites for any single optional practice:

  • An editable Guide Page template with controlled policies.
  • A Guide Card proxy component with configured and empty states.
  • Reusable Guide content with an explicit Page, Experience Fragment or Content Fragment decision.
  • A Guide List that retrieves tagged guide pages through a bounded query.
  • One controlled MSM live-copy relationship with a documented local override.
  • Responsive styling, keyboard access and useful metadata.
  • Tests, permissions, Dispatcher rules and an operational runbook.

Repository model

  1. Before Week 1, each developer chooses one starting method from the setup guide: clone the public Adobe WKND tutorial repository or generate a clean project with the AEM Project Archetype.
  2. Each developer creates an empty personal repository, publishes the untouched starting project there and tags that commit training-baseline. The tag is a Git reference, not a separate repository or branch.
  3. Anyone who chooses to implement a practice works independently; no practice depends on another learner's branch, environment or earlier optional work.
  4. If sharing code for feedback, use practice/week-<number>-short-name and a PR or diff against your own main.
  5. A peer may review a shared PR; the repository owner remains responsible for its implementation and explanation.
  6. Do not copy commits or cherry-pick another learner's implementation. Official documentation and the selected starting source are allowed.

Weekly delivery rhythm

No project board is required. Introduce the practice and its starting example on Monday. Exploring the example is enough to participate; implementing the extension is optional. Share a PR, diff or focused question before Friday only if feedback would help. The instructor prepares a complete demo even when nobody submits work.

Friday recap and demos · 30–60 minutes

  1. 30-minute version: 5 minutes of recap, 15 of prepared or voluntary demos and 10 of questions and feedback.
  2. 60-minute version: 10 minutes of recap, 30 of demos and 20 of questions and feedback.

Friday introduces no new requirement. If no one volunteers, the instructor demonstrates the supplied case, including a failure and its correction. The final Friday also includes a retrospective.

Checks for self-assessment and optional feedback

  • For an implemented extension, run its relevant local build or test and keep generated files and secrets out of the repository.
  • Show the observable result and one useful negative or regression check appropriate to the week.
  • If sharing for feedback, include reproducible steps, the smallest relevant diff and one question or remaining risk.

For Weeks 6–11, the short route is to run or inspect the supplied example, change one input and explain the result. The full route implements the listed extension. The suggested times are 30–60 minutes for exploration and about 4–6 hours for implementation, up to 6–8 hours for the larger Weeks 9 and 11 cases; these are not requirements.

The original Weeks 1–5 briefs below are retained as written. Their “must include,” submission and acceptance wording now serves as an implementation checklist for anyone who elects to do the full practice, not a participation or grading requirement.

Week 1 practice · Establish the individual baseline

Goal: create a reproducible WKND repository and local SDK, then explain how one page maps to the project.

Starting point: there is no custom baseline repository to request. Each developer chooses A) clone the public Adobe WKND tutorial repository, or B) generate a clean project with the AEM Project Archetype command in the setup guide.

  • Follow either approved setup option and publish the untouched result to an empty repository owned by you.
  • Before changing code, confirm that origin points to your repository and that the starting commit has the tag training-baseline:
git remote -v
git tag --list training-baseline

The setup guide creates the tag before any practice change. Once it is visible, create the Week 1 branch:

git switch -c practice/week-1-baseline
  • Build and install the project on local Author.
  • Map core, ui.apps, ui.content, ui.config, dispatcher and all.
  • Trace one page URL to its resource type and HTL script.

Acceptance: clean clone instructions work, Maven reports BUILD SUCCESS, WKND opens in Sites and the repository map is correct. Evidence: PR, reactor summary and annotated trace.

PR must include

  • A short README with required versions and exact clone, build, install and Author startup steps.
  • An annotated module map covering core, ui.apps, ui.content, ui.config, dispatcher and all.
  • The page URL, JCR content path, sling:resourceType and resolved HTL path used in the trace.
  • No SDK archives, license files, logs, secrets, generated target directories or local configuration.

Developer must show

  • A clean Maven reactor ending in BUILD SUCCESS and the commit being reviewed.
  • Local Author running, WKND visible in Sites and the traced page rendering.
  • How the browser URL resolves to content, resource type, module and HTL script.
  • Which module would own one Java, component, content, configuration and Dispatcher change.

Week 2 practice · Create the Guide Page authoring contract

Goal: create a governed Guide Page that an author can use consistently without developer intervention.

  • Define required fields, defaults and empty states.
  • Create the editable template and initial structure.
  • Configure policies, allowed components and author-facing styles.
  • Create one guide page with an accessible image and metadata.

Acceptance: a new Guide Page can be created and edited from the template; policy restrictions and image alternative-text behavior are observable. Evidence: paths, authored page and authoring walkthrough.

PR must include

  • Only the required template, initial structure, policy and allowed-component definitions under the appropriate /conf package paths.
  • Readable names, descriptions and defaults for author-facing configuration.
  • Any necessary content-package filter change, kept as narrow as the new paths.
  • PR evidence showing the created page; mutable authored content is not exported into code unless the baseline explicitly requires sample content.

Developer must show

  • Creating a new Guide Page from the template, not only editing an existing page.
  • Allowed and disallowed components in the container plus one Style System choice.
  • Where the template structure, policy and authored properties live in the repository.
  • Image and metadata behavior with both valid and missing alternative text.

Week 3 practice · Deliver the Guide Card frontend slice

Goal: deliver a responsive and accessible Guide Card that exposes the complete dialog-to-browser path.

  • Create a project-owned proxy component without copying product implementation.
  • Add the dialog and persist the smallest required property set.
  • Render configured and empty states with safe HTL.
  • Add scoped CSS/JavaScript only where native HTML and CSS are insufficient.
  • Inspect the Core Component Data Layer contract and preserve it through the proxy.
  • Check keyboard, focus, long text, 200% zoom and narrow width.

Acceptance: dialog → property → HTL → browser works; the existing Data Layer contract remains observable and the component passes the stated accessibility and responsive checks. Evidence: PR, two component states, Data Layer state and executed checklist.

PR must include

  • The project-owned proxy component definition, explicit sling:resourceSuperType, dialog and HTL.
  • Scoped client-library CSS and only the JavaScript required for behavior that native HTML/CSS cannot provide.
  • Configured and empty-state markup with correct HTL display contexts and no copied Core Component implementation.
  • Evidence of the resulting Data Layer state, with custom tracking code only when the stated requirement needs it.
  • A completed accessibility/responsive checklist and screenshots or short recordings for both states.

Developer must show

  • The complete dialog field → JCR property → HTL expression → rendered DOM trace.
  • Configured and empty author states without template errors or broken controls.
  • Keyboard operation, visible focus, long text, narrow viewport and 200% zoom.
  • Why each custom CSS or JavaScript rule is necessary and where its clientlib is loaded.
  • Which component values are exposed through the existing Data Layer contract.

Week 4 practice · Add server-side behavior and tests

Goal: provide view-ready Guide Card data while keeping HTL simple and missing content safe.

  • Add a Sling Model only for behavior that HTL should not own.
  • Use explicit optionality and safe fallbacks.
  • Add a small OSGi configuration only if the behavior varies by environment.
  • Write focused JUnit 5 tests with AEM Mocks for configured, missing and invalid input.
  • Compare HTL, .model.json and servlet options; document why a new endpoint is or is not required.

Acceptance: configured, missing and legacy content render without exceptions; at least one test fails without the implementation and the HTML/JSON/servlet decision names the actual consumer. Evidence: model/service diff, JUnit output and endpoint decision.

PR must include

  • A focused Sling Model in core with the correct adaptable, resource type and explicit injection optionality.
  • View-ready getters and safe fallbacks; HTL must not contain business or formatting logic moved from Java.
  • JUnit 5 and AEM Mocks tests for configured, missing and invalid or legacy input, including one assertion that fails without the change.
  • OSGi configuration only for environment-varying behavior and a brief decision comparing HTL, an existing Model Exporter contract and a servlet.

Developer must show

  • The focused test command and passing output, then identify which regression each test protects.
  • Model adaptation from a representative resource and the behavior when a property is absent.
  • The rendered configured, empty and legacy states without exceptions in the log.
  • Why the boundary belongs in HTL, a Sling Model, Model Exporter, service or servlet.

Week 5 practice · Maintain reusable and multi-site Guide content

Goal: trace reusable Guide content and one MSM relationship, then diagnose a failure at a reference, inheritance or asynchronous-processing boundary.

  • Inspect one existing Experience Fragment and one Content Fragment from authoring to repository storage and page consumption.
  • Select Page, XF or CF for one reusable Weekend Guides requirement and document the ownership and publication reason.
  • Trace language master → Live Copy, cancel inheritance for one component and execute one controlled rollout.
  • Reproduce and fix a seeded missing-reference, inheritance or workflow/job symptom at its smallest common source.
  • Verify that rebuilds preserve authored fragments, live-copy state and guide content.

Acceptance: both fragment traces are correct, the rollout changes only the intended inherited value, the local override remains intact and the seeded symptom passes with regression evidence. Evidence: fragment traces, MSM matrix, incident note and focused diff.

PR must include

  • Two concise traces: XF/CF authoring location → stored Resource → consuming page → publication dependency.
  • A Page/XF/CF decision naming content ownership, layout responsibility, reuse scope and rejected option; GraphQL is out of scope.
  • An MSM matrix recording source, Live Copy, inherited or local state, action and observed result.
  • A concise incident note: symptom, minimal reproduction, hypothesis, evidence, root cause, fix and remaining risk.
  • A focused root-cause diff with no unrelated refactor or formatting churn.
  • A regression test or repeatable command that fails before the fix and passes after it.
  • Verification that build and installation do not overwrite mutable fragments, Live Copy state or authored Guide content.

Developer must show

  • Where the XF and CF live, how each is referenced and which related item must reach Publish.
  • The language master and Live Copy relationship before and after canceling inheritance and rollout.
  • The original symptom reproduced from a known state and the reference, relationship, workflow or job path that connects it to the cause.
  • The regression check failing before the correction and passing on the reviewed commit.
  • The local override or adjacent reference used to prove the fix is not a destructive global workaround.

Week 6 practice · Bounded Guide List and least-privilege access

Goal: return the right Guide Pages, explain the query plan and correct an access failure without widening permissions.

Starting point: the instructor supplies tagged Guide Pages with included, excluded and unreadable cases, a costly query and a small technical operation. The query and permissions examples provide local reference steps.

Explore the example: change a tag or identity, compare the resulting list and explain which path or permission excluded a page.

Implement the extension:

  • Build one Guide List query constrained by path, resource type and tag, with a finite result window and pagination. Use JCR-SQL2 to inspect or compare the plan, not to duplicate the implementation.
  • Compare the original and corrected query plans and observed work. Justify the existing index; propose a Cloud-compatible index change only when the case demonstrates the need.
  • Define the technical operation's service user and narrow ACL with Repo Init, then connect its subservice mapping. Keep visitor-facing reads under the request identity when visibility depends on the visitor.
  • Check allowed and excluded reads plus denied writes in a real local repository; distinguish a missing mapping from an ACL denial.

Self-check: the list includes intended pages, excludes the negative fixture, stays bounded, and the access test shows the intended identity and result. An index name alone is not proof of an efficient query.

For feedback or Friday demo: share a diff, query and plan, an identity/path/operation/result table and one repeatable regression check. Show one correct result, one exclusion and the access failure's cause.

Week 7 practice · Publish a guide and diagnose stale or missing content

Goal: serve a Guide Page and its dependencies through local Publish and Dispatcher, then identify the layer behind a missing or outdated response.

Starting point: the instructor supplies a page with a fragment or asset dependency, a local Dispatcher case and clearly labeled CDN headers or logs. Use the local Publish and Dispatcher setup if running the exercise.

Explore the example: compare the same URL on Author, Publish and Dispatcher; change one published dependency or request header and identify the first divergent response.

Implement the extension:

  • Publish the page and required fragment or asset, then verify the resource on Publish.
  • Test one permitted and one blocked request and one specific redirect or rewrite, naming the responsible vhost, farm or filter rule.
  • Reproduce a cache miss, hit and controlled refresh after a content change; correct the seeded stale or missing-content symptom without clearing all caches.
  • Explain the supplied CDN case separately from local Publish and Dispatcher evidence, including one response that must stay out of shared cache.

Self-check: HTTP status, Location, relevant headers and logs support the layer diagnosis; the corrected response and a control request behave as expected. Local publication does not prove Cloud distribution behavior.

For feedback or Friday demo: share reproducible HTTP commands, the focused config or content change and before/after responses. Reproduce the symptom, show the fix and run a control request.

Week 8 practice · Diagnose a Cloud-compatible delivery

Goal: locate the first actionable delivery or configuration failure and verify a correction locally without requiring Cloud access.

Starting point: the instructor supplies a labeled synthetic case with a commit, pipeline type, failure log, configuration and service state, plus a locally reproducible defect.

Explore the example: identify the pipeline and destination, point to the first actionable error and choose the Cloud inspection tool that would test your hypothesis.

Implement the extension:

  • Trace commit → build artifact → relevant quality gate → target environment, separating the primary failure from later messages.
  • Correct the supplied build, package or OSGi configuration defect and run the focused local check.
  • Distinguish versioned .cfg.json values, environment variables and secret references; include no live credentials.
  • Check the corrected change against the older fixture content and explain recovery if old and new versions coexist during delivery.

Self-check: the local defect fails before and passes after the fix, while the diagnostic note states what supplied Cloud evidence supports and what remains untested. RDE does not replace pipeline validation.

For feedback or Friday demo: share the diagnostic map, focused diff, command and result. Show the first actionable error and the local correction without claiming a Cloud Manager run.

Week 9 practice · Retry a safe asynchronous update

Goal: make one Author-side Sling Job tolerate a transient HTTP failure and a repeated attempt without duplicating its business effect.

Starting point: the instructor supplies a minimal job, controllable local HTTP stub, narrow service identity and one prepared MSM or Content Fragment reference case.

Explore the example: trigger a failed response and a retry with the same business key; observe the stored status and resulting content.

Implement the extension:

  • Add a bounded timeout, explicit handling for transient and permanent HTTP responses, and a repeatable operation keyed to the business item.
  • Use the exercise's least-privilege subservice and persist enough progress to resume after a restart; do not rely on memory alone.
  • Show success, transient failure and replay without a duplicate effect. State that a local check does not prove cluster-wide coordination.
  • Inspect one supplied MSM or Content Fragment reference case and explain the consequence of changing its source; no additional subsystem is required.

Self-check: the retry completes after the stub recovers, replay leaves one intended effect, and the job's status explains what happened. A timeout does not prove the remote service did nothing.

For feedback or Friday demo: share the diff, attempt/result sequence, replay check and short content-impact decision. Induce the failure and demonstrate controlled recovery.

Week 10 practice · Catch a regression and measure one improvement

Goal: detect a relevant regression and correct one accessibility, SEO or performance defect with comparable evidence.

Starting point: the instructor supplies a stable Weekend Guides fixture, existing unit tests, a chosen UI test tool and commands for local HTTP checks and measurement.

Explore the example: run one existing check, vary a failing input and compare the resulting browser or HTTP behavior.

Implement the extension:

  • Extend one existing unit test with a negative case that fails before the correction.
  • Add one real repository or HTTP check for a behavior AEM Mocks cannot prove, and automate one critical author-to-visible-page UI route with the chosen tool.
  • Inspect keyboard, focus and relevant metadata; measure one load, query or rendering problem under comparable conditions.
  • Correct the highest-priority finding and record remaining risks without adding an unnecessary framework or broad test suite.

Self-check: the regression test and local integration/UI checks run, and a before/after measure supports the selected improvement. A Lighthouse score alone does not establish accessibility conformance.

For feedback or Friday demo: share test output, a short checklist, measurement conditions and a focused diff. Show the failing and passing case and why each test level was chosen.

Week 11 practice · Optional integrated troubleshooting case

Goal: trace one Weekend Guides incident across layers and explain an evidence-backed correction using the supplied case or a voluntary personal extension.

Starting point: the instructor supplies a complete integrated example, a bounded incident and a prepared demo; no previous practice implementation is needed.

Explore the example: follow browser → CDN evidence → Dispatcher → Sling → Model → OSGi → JCR, change one input and identify the first divergent layer.

Implement the extension, if desired:

  • Reproduce the incident from a known state, rank plausible causes and run the next check that best separates them.
  • Make the smallest correction or implement one optional requirement variation on the supplied example or personal project.
  • Repeat the relevant regression and control checks; record recovery steps and one unresolved limitation.

Self-check: you can follow the trace, reproduce the result and explain one technical decision. Asking for help is part of the exercise; there is no exam, grade or required individual defense.

For feedback or final Friday: optionally share the diff, trace, checks and a specific question before Friday. Volunteers may show a short demo or recording; the instructor's prepared demo and retrospective close the course even if no one submits work.

Code similarity and understanding protocol

Similarities may occur because participants use the same starter and examples. When someone voluntarily shares code for feedback, use a comparison to guide a conversation, never as an automatic plagiarism score.

  1. Compare only learner-authored changes. Diff each repository from training-baseline. Exclude generated files, target, lockfiles, supplied starter code and formatting-only changes.
  2. Look for meaningful matches. Identical custom names, comments, unusual control flow, mistakes or commit sequence are stronger signals than standard AEM patterns.
  3. Do not set a similarity percentage threshold. Two correct proxy components will naturally share structure.
  4. Discuss understanding. If the participant requests feedback, ask them to explain one path and lifecycle, run the relevant check or try a small variation.
  5. Give descriptive feedback. Record what the participant demonstrated and a useful next check; do not assign a grade or proficiency level.

A dependency is unnecessary here: git diff training-baseline...HEAD isolates each submission, and git diff --no-index can compare two selected learner-authored directories when a closer review is warranted.
