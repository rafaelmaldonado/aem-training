Eight weekly practices · one developer per repository

Individual WKND practices.

The architect releases one common practice every Monday. Each developer completes it in an individual repository and local AEM SDK, submits evidence by Thursday and reviews it on Friday.

  • Released Monday
  • Due Thursday
  • Reviewed Friday
Delivery constraint: no shared deployment environment is required. Each developer owns a repository and local SDK created from the same read-only baseline. Cloud delivery is demonstrated or rehearsed with supplied pipeline evidence when access is unavailable.

Product scenario

Each developer inherits the same WKND baseline and adds a Weekend Guides area. Authors must create guide pages and reusable cards without code changes. Visitors must browse accessible, responsive content. The implementation must be testable, cache-safe and compatible with an AEMaaCS pipeline.

  • An editable Guide Page template with controlled policies.
  • A Guide Card proxy component with configured and empty states.
  • A Guide List that retrieves and orders guide pages.
  • Responsive styling, keyboard access and useful metadata.
  • Tests, permissions, Dispatcher rules and an operational runbook.

Repository model

  1. The architect publishes one read-only baseline generated with the command in the setup guide and tags it training-baseline.
  2. Each developer creates a private fork or repository from that baseline and runs an individual local Author SDK.
  3. Every developer completes the same weekly practice; there are no dependencies on another learner's branch or environment.
  4. Each practice uses practice/week-<number>-short-name and one PR into that developer's own main.
  5. A peer may review the PR, but only the repository owner implements, fixes and demonstrates the practice.
  6. Do not copy commits or cherry-pick another learner's implementation. Official documentation and the supplied baseline are allowed sources.

Weekly delivery rhythm

No project board is required. Publish the practice brief on Monday and use one issue or PR per developer as the delivery record. The architect tracks only its link and demonstrated proficiency in the existing evidence sheet.

MomentActivityOutput
MondayArchitect releases the goal, starting point, constraints, acceptance and evidence.One common practice brief.
Tuesday–WednesdayDeveloper implements independently and asks focused questions when blocked.Branch and working commits.
ThursdayDeveloper opens or updates the PR and submits all required evidence.Reviewable PR before close of day.
FridayArchitect reviews common findings; two developers demonstrate on rotation; selected owners explain or vary their code.Feedback, proficiency level and next check.

Friday review session · 30 minutes

  1. 0–3 min: retrieval question without notes.
  2. 3–15 min: two rotating demonstrations, six minutes each.
  3. 15–25 min: common findings, alternatives and one small understanding check.
  4. 25–30 min: proficiency result, corrections and next week's bridge.

All six submissions are reviewed asynchronously before the session. Friday is for representative evidence and technical reasoning, not six status reports.

Weekly completion criteria

  • mvn clean verify succeeds and no generated target files or secrets are committed.
  • The change installs and runs in the developer's local SDK.
  • The PR contains reproducible author, visitor, test or diagnostic evidence appropriate to the practice.
  • The developer explains where the change lives, why it belongs there and one remaining risk.
  • The developer can make a small requested variation without following another implementation.

Week 1 practice · Establish the individual baseline

Goal: create a reproducible WKND repository and local SDK, then explain how one page maps to the project.

  • Fork or create the repository from training-baseline.
  • Build and install the project on local Author.
  • Map core, ui.apps, ui.content, ui.config, dispatcher and all.
  • Trace one page URL to its resource type and HTL script.

Acceptance: clean clone instructions work, Maven reports BUILD SUCCESS, WKND opens in Sites and the repository map is correct. Evidence: PR, reactor summary and annotated trace.

Week 2 practice · Create the Guide Page authoring contract

Goal: create a governed Guide Page that an author can use consistently without developer intervention.

  • Define required fields, defaults and empty states.
  • Create the editable template and initial structure.
  • Configure policies, allowed components and author-facing styles.
  • Create one guide page with an accessible image and metadata.

Acceptance: a new Guide Page can be created and edited from the template; policy restrictions and image alternative-text behavior are observable. Evidence: paths, authored page and authoring walkthrough.

Week 3 practice · Deliver the Guide Card frontend slice

Goal: deliver a responsive and accessible Guide Card that exposes the complete dialog-to-browser path.

  • Create a project-owned proxy component without copying product implementation.
  • Add the dialog and persist the smallest required property set.
  • Render configured and empty states with safe HTL.
  • Add scoped CSS/JavaScript only where native HTML and CSS are insufficient.
  • Check keyboard, focus, long text, 200% zoom and narrow width.

Acceptance: dialog → property → HTL → browser works; the component passes the stated accessibility and responsive checks. Evidence: PR, two component states and executed checklist.

Week 4 practice · Add server-side behavior and tests

Goal: provide view-ready Guide Card data while keeping HTL simple and missing content safe.

  • Add a Sling Model only for behavior that HTL should not own.
  • Use explicit optionality and safe fallbacks.
  • Add a small OSGi configuration only if the behavior varies by environment.
  • Write focused tests for configured, missing and invalid input.
  • Document why a servlet is or is not required.

Acceptance: configured, missing and legacy content render without exceptions; at least one test fails without the implementation. Evidence: model/service diff, test output and endpoint decision.

Week 5 practice · Diagnose and fix a maintenance defect

Goal: diagnose an unfamiliar Weekend Guides defect and correct its root cause without a local workaround.

  • Reproduce the seeded symptom and name the affected layer.
  • Trace callers or configuration consumers before editing.
  • Fix the smallest common source and add regression evidence.
  • Verify that rebuilds do not overwrite authored guide content.
  • Record hypothesis, test, conclusion and remaining risk.

Acceptance: the original symptom and one adjacent case pass; the report connects evidence to the root cause. Evidence: incident note, focused diff and regression check.

Week 6 practice · Rehearse cloud delivery locally

Goal: complete a reproducible delivery rehearsal covering pipeline, Dispatcher and cache behavior without a shared cloud environment.

  • Map commit → build → quality gates → deployment using supplied Cloud Manager evidence.
  • Analyze one anonymized failed pipeline log and identify the first actionable error.
  • Validate a narrow Dispatcher filter or rewrite with local Dispatcher Tools.
  • Explain a cache hit, miss and invalidation from supplied headers or a controlled local lab.
  • Write a short deployment and recovery runbook.

Acceptance: every gate has evidence, the Dispatcher rule preserves deny-by-default and the runbook distinguishes what was executed from what was simulated. Evidence: annotated log, rule test and runbook.

Week 7 practice · Complete a production-readiness review

Goal: review the Guide feature across production risks and fix the most important reproducible finding.

  • Review permissions and service-user access for least privilege.
  • Review output encoding, validation, CSRF/XSS exposure and secrets.
  • Audit keyboard, semantics, headings, metadata and zoom.
  • Select the cheapest meaningful performance and regression checks.
  • Fix the highest-risk reproducible finding.

Acceptance: findings are evidence-based and prioritized; the selected fix has before/after proof and does not break authoring. Evidence: review matrix, PR and verification.

Week 8 practice · Deliver and defend the individual capstone

Goal: deliver one complete Weekend Guides increment and demonstrate independent AEM ownership from authoring to operation.

  • Choose one observable author or visitor outcome not implemented in the supplied baseline.
  • Refine acceptance criteria, dependencies and risks before coding.
  • Implement in coherent commits and harden against review findings.
  • Demonstrate authoring, visitor behavior, tests and operational checks.
  • Complete a short technical defense and define one 30-day growth outcome.

Acceptance: the developer can explain and modify the implementation without direct help; the demo includes working behavior, evidence and one remaining risk. Evidence: final PR, demo and technical defense.

Code similarity and understanding protocol

Similarity is expected because everyone starts from the same archetype and completes the same practice. Use it to select follow-up questions, not as an automatic plagiarism score.

  1. Compare only learner-authored changes. Diff each repository from training-baseline. Exclude generated files, target, lockfiles, supplied starter code and formatting-only changes.
  2. Look for meaningful matches. Identical custom names, comments, unusual control flow, mistakes or commit sequence are stronger signals than standard AEM patterns.
  3. Do not set a similarity percentage threshold. Two correct proxy components will naturally share structure.
  4. Verify understanding. Ask the developer to explain one path and lifecycle, run the relevant check, then make a small variation such as changing a fallback, validation rule or empty state.
  5. Record the result. Similar code passes when the owner can explain, test and adapt it. It remains unverified when the owner cannot reproduce or modify the behavior.

A dependency is unnecessary here: git diff training-baseline...HEAD isolates each submission, and git diff --no-index can compare two selected learner-authored directories when a closer review is warranted.
