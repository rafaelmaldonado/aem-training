Seven weekly practices · one developer per repository

Individual WKND practices.

The architect releases one common practice every Monday. Each developer completes it in an individual repository and local AEM SDK, submits evidence by Thursday and reviews it on Friday.

  • Released Monday
  • Due Thursday
  • Reviewed Friday
Delivery constraint: no shared deployment environment or Cloud Manager access is required. Each developer owns a repository and local SDK created with the same selected starting method. Cloud Manager is studied from supplied diagrams and anonymized evidence; hands-on checks run locally.

Product scenario

Each developer starts from the same selected WKND source and adds a Weekend Guides area. Authors must create guide pages and reusable cards without code changes. Visitors must browse accessible, responsive content. The implementation must be testable, cache-safe and compatible with an AEMaaCS pipeline.

  • An editable Guide Page template with controlled policies.
  • A Guide Card proxy component with configured and empty states.
  • A Guide List that retrieves and orders guide pages.
  • Responsive styling, keyboard access and useful metadata.
  • Tests, permissions, Dispatcher rules and an operational runbook.

Repository model

  1. Before Week 1, the instructor selects one starting method from the setup guide: clone the public Adobe WKND repository or generate a clean project with the AEM Project Archetype.
  2. Each developer creates an empty personal repository, publishes the untouched starting project there and tags that commit training-baseline. The tag is a Git reference, not a separate repository or branch.
  3. Every developer completes the same weekly practice; there are no dependencies on another learner's branch or environment.
  4. Each practice uses practice/week-<number>-short-name and one PR into that developer's own main.
  5. A peer may review the PR, but only the repository owner implements, fixes and demonstrates the practice.
  6. Do not copy commits or cherry-pick another learner's implementation. Official documentation and the selected starting source are allowed.

Weekly delivery rhythm

No project board is required. Publish the practice brief on Monday and use one issue or PR per developer as the delivery record. The architect tracks only its link and demonstrated proficiency in the existing evidence sheet.

MomentActivityOutput
MondayArchitect releases the goal, starting point, constraints, acceptance and evidence.One common practice brief.
Tuesday–WednesdayDeveloper implements independently and asks focused questions when blocked.Branch and working commits.
ThursdayDeveloper opens or updates the PR and submits all required evidence.Reviewable PR before close of day.
FridayArchitect reviews common findings; two developers demonstrate on rotation; selected owners explain or vary their code.Feedback, proficiency level and next check.

Friday review session · 30 minutes

  1. 0–3 min: retrieval question without notes.
  2. 3–15 min: two rotating demonstrations, six minutes each.
  3. 15–25 min: common findings, alternatives and one small understanding check.
  4. 25–30 min: proficiency result, corrections and next week's bridge.

All six submissions are reviewed asynchronously before the session. Friday is for representative evidence and technical reasoning, not six status reports.

Weekly completion criteria

  • mvn clean verify succeeds and no generated target files or secrets are committed.
  • The change installs and runs in the developer's local SDK.
  • The PR contains reproducible author, visitor, test or diagnostic evidence appropriate to the practice.
  • The developer explains where the change lives, why it belongs there and one remaining risk.
  • The developer can make a small requested variation without following another implementation.

Week 1 practice · Establish the individual baseline

Goal: create a reproducible WKND repository and local SDK, then explain how one page maps to the project.

Starting point: there is no custom baseline repository to request. The instructor announces one common option for the group: A) start from the public Adobe WKND repository, or B) generate a clean project with the AEM Project Archetype command in the setup guide.

  • Follow the selected setup option and publish the untouched result to an empty repository owned by you.
  • Before changing code, confirm that origin points to your repository and that the starting commit has the tag training-baseline:
git remote -v
git tag --list training-baseline

The setup guide creates the tag before any practice change. Once it is visible, create the Week 1 branch:

git switch -c practice/week-1-baseline
  • Build and install the project on local Author.
  • Map core, ui.apps, ui.content, ui.config, dispatcher and all.
  • Trace one page URL to its resource type and HTL script.

Acceptance: clean clone instructions work, Maven reports BUILD SUCCESS, WKND opens in Sites and the repository map is correct. Evidence: PR, reactor summary and annotated trace.

PR must include

  • A short README with required versions and exact clone, build, install and Author startup steps.
  • An annotated module map covering core, ui.apps, ui.content, ui.config, dispatcher and all.
  • The page URL, JCR content path, sling:resourceType and resolved HTL path used in the trace.
  • No SDK archives, license files, logs, secrets, generated target directories or local configuration.

Developer must show

  • A clean Maven reactor ending in BUILD SUCCESS and the commit being reviewed.
  • Local Author running, WKND visible in Sites and the traced page rendering.
  • How the browser URL resolves to content, resource type, module and HTL script.
  • Which module would own one Java, component, content, configuration and Dispatcher change.

Week 2 practice · Create the Guide Page authoring contract

Goal: create a governed Guide Page that an author can use consistently without developer intervention.

  • Define required fields, defaults and empty states.
  • Create the editable template and initial structure.
  • Configure policies, allowed components and author-facing styles.
  • Create one guide page with an accessible image and metadata.

Acceptance: a new Guide Page can be created and edited from the template; policy restrictions and image alternative-text behavior are observable. Evidence: paths, authored page and authoring walkthrough.

PR must include

  • Only the required template, initial structure, policy and allowed-component definitions under the appropriate /conf package paths.
  • Readable names, descriptions and defaults for author-facing configuration.
  • Any necessary content-package filter change, kept as narrow as the new paths.
  • PR evidence showing the created page; mutable authored content is not exported into code unless the baseline explicitly requires sample content.

Developer must show

  • Creating a new Guide Page from the template, not only editing an existing page.
  • Allowed and disallowed components in the container plus one Style System choice.
  • Where the template structure, policy and authored properties live in the repository.
  • Image and metadata behavior with both valid and missing alternative text.

Week 3 practice · Deliver the Guide Card frontend slice

Goal: deliver a responsive and accessible Guide Card that exposes the complete dialog-to-browser path.

  • Create a project-owned proxy component without copying product implementation.
  • Add the dialog and persist the smallest required property set.
  • Render configured and empty states with safe HTL.
  • Add scoped CSS/JavaScript only where native HTML and CSS are insufficient.
  • Check keyboard, focus, long text, 200% zoom and narrow width.

Acceptance: dialog → property → HTL → browser works; the component passes the stated accessibility and responsive checks. Evidence: PR, two component states and executed checklist.

PR must include

  • The project-owned proxy component definition, explicit sling:resourceSuperType, dialog and HTL.
  • Scoped client-library CSS and only the JavaScript required for behavior that native HTML/CSS cannot provide.
  • Configured and empty-state markup with correct HTL display contexts and no copied Core Component implementation.
  • A completed accessibility/responsive checklist and screenshots or short recordings for both states.

Developer must show

  • The complete dialog field → JCR property → HTL expression → rendered DOM trace.
  • Configured and empty author states without template errors or broken controls.
  • Keyboard operation, visible focus, long text, narrow viewport and 200% zoom.
  • Why each custom CSS or JavaScript rule is necessary and where its clientlib is loaded.

Week 4 practice · Add server-side behavior and tests

Goal: provide view-ready Guide Card data while keeping HTL simple and missing content safe.

  • Add a Sling Model only for behavior that HTL should not own.
  • Use explicit optionality and safe fallbacks.
  • Add a small OSGi configuration only if the behavior varies by environment.
  • Write focused tests for configured, missing and invalid input.
  • Document why a servlet is or is not required.

Acceptance: configured, missing and legacy content render without exceptions; at least one test fails without the implementation. Evidence: model/service diff, test output and endpoint decision.

PR must include

  • A focused Sling Model in core with the correct adaptable, resource type and explicit injection optionality.
  • View-ready getters and safe fallbacks; HTL must not contain business or formatting logic moved from Java.
  • Unit tests for configured, missing and invalid or legacy input, including one assertion that fails without the change.
  • OSGi configuration only for environment-varying behavior and a brief decision explaining why no servlet is needed, or the endpoint contract if one is.

Developer must show

  • The focused test command and passing output, then identify which regression each test protects.
  • Model adaptation from a representative resource and the behavior when a property is absent.
  • The rendered configured, empty and legacy states without exceptions in the log.
  • Why the boundary belongs in a Sling Model, service or servlet rather than HTL.

Week 5 practice · Diagnose and fix a maintenance defect

Goal: diagnose an unfamiliar Weekend Guides defect and correct its root cause without a local workaround.

  • Reproduce the seeded symptom and name the affected layer.
  • Trace callers or configuration consumers before editing.
  • Fix the smallest common source and add regression evidence.
  • Verify that rebuilds do not overwrite authored guide content.
  • Record hypothesis, test, conclusion and remaining risk.

Acceptance: the original symptom and one adjacent case pass; the report connects evidence to the root cause. Evidence: incident note, focused diff and regression check.

PR must include

  • A concise incident note: symptom, minimal reproduction, hypothesis, evidence, root cause, fix and remaining risk.
  • A focused root-cause diff with no unrelated refactor or formatting churn.
  • A regression test or repeatable command that fails before the fix and passes after it.
  • Verification that the change does not overwrite mutable authored content during rebuild or installation.

Developer must show

  • The original symptom reproduced from a known starting state.
  • The caller, configuration or resolution path that connects the symptom to the cause.
  • The regression check failing before the correction and passing on the reviewed commit.
  • The adjacent case used to prove the fix is not a one-page workaround.

Week 6 practice · Complete a local production-readiness review

Goal: harden the Guide feature with local security, accessibility, performance, Dispatcher and test evidence while explaining the supplied cloud-delivery model.

  • Map commit → build → quality gates → environment using supplied Cloud Manager diagrams and logs; do not execute or simulate access.
  • Validate a narrow Dispatcher filter or rewrite with local Dispatcher Tools.
  • Review permissions, output security, secrets, keyboard use, semantics and metadata.
  • Run the cheapest meaningful regression and performance checks.
  • Fix the highest-risk reproducible local finding.

Acceptance: Cloud Manager concepts are explained from supplied evidence, local controls are executed, and the selected risk has reproducible before/after proof. Evidence: delivery map, readiness matrix, focused fix and verification.

PR must include

  • A one-page theoretical delivery map naming repository, branch, build, quality gates, environment and likely failure owner.
  • Any Dispatcher change in the correct module with the narrowest filter, rewrite or cache rule that meets the requirement.
  • A readiness matrix covering functionality, authoring, security, permissions, accessibility, SEO, performance, testing and operation.
  • The highest-risk focused correction, its regression check and before/after evidence; no credentials, private URLs or raw environment dumps.

Developer must show

  • The supplied commit-to-environment flow and first actionable error without claiming Cloud Manager access.
  • One allowed and one denied Dispatcher request with the exact rule responsible.
  • One least-privilege or output-security control plus keyboard, zoom and metadata checks.
  • Why the selected local finding outranks the others and which regression or performance check proves the improvement.

Week 7 practice · Deliver and defend the individual capstone

Goal: deliver one complete Weekend Guides increment and demonstrate independent AEM ownership from authoring to operation.

  • Choose one observable author or visitor outcome not implemented in the selected starting project.
  • Refine acceptance criteria, dependencies and risks before coding.
  • Implement in coherent commits and harden against review findings.
  • Demonstrate authoring, visitor behavior, tests and operational checks.
  • Complete a short technical defense and define one 30-day growth outcome.

Acceptance: the developer can explain and modify the implementation without direct help; the demo includes working behavior, evidence and one remaining risk. Evidence: final PR, demo and technical defense.

PR must include

  • An observable author or visitor outcome, explicit acceptance criteria, dependencies and known risks in the PR description.
  • Coherent commits covering the minimum code, content configuration, tests and operational documentation needed for the increment.
  • Clean build output, focused test results, author/visitor evidence and the production-readiness checks relevant to the change.
  • Resolved review comments, one remaining risk and a safe rollback or recovery note.

Developer must show

  • The complete author and visitor journey from a clean local starting state.
  • The most important automated check and one production-readiness control.
  • Where the implementation lives and why three key technical decisions were made.
  • A small requested variation implemented and verified during the technical defense.

Code similarity and understanding protocol

Similarity is expected because everyone starts from the same archetype and completes the same practice. Use it to select follow-up questions, not as an automatic plagiarism score.

  1. Compare only learner-authored changes. Diff each repository from training-baseline. Exclude generated files, target, lockfiles, supplied starter code and formatting-only changes.
  2. Look for meaningful matches. Identical custom names, comments, unusual control flow, mistakes or commit sequence are stronger signals than standard AEM patterns.
  3. Do not set a similarity percentage threshold. Two correct proxy components will naturally share structure.
  4. Verify understanding. Ask the developer to explain one path and lifecycle, run the relevant check, then make a small variation such as changing a fallback, validation rule or empty state.
  5. Record the result. Similar code passes when the owner can explain, test and adapt it. It remains unverified when the owner cannot reproduce or modify the behavior.

A dependency is unnecessary here: git diff training-baseline...HEAD isolates each submission, and git diff --no-index can compare two selected learner-authored directories when a closer review is warranted.
