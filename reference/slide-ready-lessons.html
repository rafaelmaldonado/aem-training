Week 1 · Mental model and environment

Day 1 · AEM Sites: from author to browser

Retrieval question: Where does an author work, and which service answers a visitor?

Open the complete illustrated six-slide deck →

  1. Slide 1 — What AEM Sites solves. Developers create reusable components and rules; authors assemble and update experiences without editing source code. Speaker cue: connect this separation to faster publishing with controlled design.
  2. Slide 2 — Author and Publish have different jobs. Author serves internal creation, review and management. Publish serves approved experiences to visitors. Speaker cue: saving on Author does not make content public.
  3. Slide 3 — The content flow. Edit → save → review → publish/distribute. Content activation is independent from a Maven deployment. Speaker cue: ask for one incident caused by confusing save and publish.
  4. Slide 4 — The request flow. Browser → CDN → Dispatcher → Publish. A cache can answer before Publish renders anything. Speaker cue: explain a cache hit and miss without introducing configuration syntax.
  5. Slide 5 — The code flow. Git → build and quality gates → deployment → AEM runtime. Deployed code renders distributed content. Speaker cue: place code and content in different colors on the diagram.

Demo: edit and preview a WKND title, then contrast Author with Publish. Assignment: draw both flows and classify five incidents by layer. Acceptance: all layers are ordered correctly and publishing is clearly different from deploying.

Day 2 · Local SDK and WKND project structure

Retrieval question: Which flow changes when a Java class changes: content or code?

  1. Slide 1 — Three parts of local development. The WKND source project, the AEM SDK runtime and Dispatcher Tools model different parts of the cloud solution. Speaker cue: today only Author and the source project are required.
  2. Slide 2 — Maven coordinates the build. The root POM controls modules, dependency versions, tests and packaging. Speaker cue: a reactor build is one coordinated product, not unrelated folders.
  3. Slide 3 — Code modules. core contains Java; ui.apps contains components, dialogs, HTL and client library definitions. Speaker cue: show one visible component in both modules.
  4. Slide 4 — Content and configuration modules. ui.content, ui.config, dispatcher and all have separate deployment responsibilities. Speaker cue: location communicates lifecycle and ownership.
  5. Slide 5 — Build before installation. mvn clean verify validates; the approved install profile deploys the complete package to local Author. Speaker cue: repository README commands override generic examples.

Demo: run the WKND build and locate the all package. Assignment: complete setup and map six change scenarios to modules. Acceptance: BUILD SUCCESS and at least five justified module choices.

Day 3 · JCR, nodes, properties and resources

Retrieval question: Which module would contain a dialog, and where would the author's value be stored?

  1. Slide 1 — AEM content is a tree. JCR stores addressable nodes and properties rather than web pages as database rows. Speaker cue: use the Sites hierarchy as the familiar entry point.
  2. Slide 2 — Sling uses resources. A resource gives application code a web-oriented view of repository content and properties. Speaker cue: prefer the Resource API unless JCR-specific behavior is required.
  3. Slide 3 — /content holds managed experiences. Pages and assets change through authoring and operations. Speaker cue: mutable does not mean uncontrolled or safe to overwrite from a package.
  4. Slide 4 — /conf holds contextual configuration. Editable templates and policies live here because authors and administrators can evolve them. Speaker cue: contrast template configuration with component code.
  5. Slide 5 — /apps is application code. Project components live under /apps; product code under /libs must never be edited. Speaker cue: overlays and proxies are controlled extension points.

Demo: follow a WKND title from Page Editor to stored properties. Assignment: document five real paths and classify their lifecycle. Acceptance: content, configuration and code are distinguished correctly.

Day 4 · How Sling resolves a request

Retrieval question: What connects a content resource to the component that renders it?

  1. Slide 1 — Sling starts with a resource. It resolves the request path before choosing rendering code. Speaker cue: AEM is content-first, not controller-route-first.
  2. Slide 2 — Resource type selects capability. sling:resourceType names the component responsible for the resource. Speaker cue: show the value on a WKND component instance.
  3. Slide 3 — Request parts guide script selection. Selectors, extension and HTTP method help Sling choose a script or servlet. Speaker cue: use a simple .html request before adding selectors.
  4. Slide 4 — Super types enable reuse. sling:resourceSuperType delegates behavior without copying the parent implementation. Speaker cue: connect this to Core Component proxies.
  5. Slide 5 — Use one repeatable trace. URL → resource → resource type → script/model → response. Speaker cue: every arrow must have a path or observable value.

Demo: trace a WKND HTML URL to its HTL script. Assignment: repeat the trace for another component and one selector. Acceptance: every transition includes evidence.

Day 5 · Diagnose by layer

Retrieval question: What is the cheapest evidence that could disprove your current hypothesis?

  1. Slide 1 — Reproduce before changing. Record URL, service, user, steps, expected result and actual result. Speaker cue: a ticket title is not a reproduction.
  2. Slide 2 — Reduce the responsible layer. Test content, configuration, render, frontend, delivery and access separately. Speaker cue: change one variable at a time.
  3. Slide 3 — State a falsifiable hypothesis. “The policy excludes the component” is testable; “AEM is broken” is not. Speaker cue: pair each hypothesis with one cheap check.
  4. Slide 4 — Prefer evidence over authority. A stored property, request, log line, effective configuration or diff can support a conclusion. Speaker cue: screenshots without context rarely identify cause.
  5. Slide 5 — Fix the shared cause. Find callers, change the smallest common source and test adjacent behavior. Speaker cue: a local workaround creates the next incident.

Demo: diagnose a component hidden by template policy. Assignment: investigate a seeded WKND symptom. Acceptance: reproduction, hypothesis, check, conclusion and remaining risk are recorded.

Week 2 · Maintainable authoring

Day 6 · Pages and editable templates

Retrieval question: Which parts of a page should be shared across every instance?

  1. Slide 1 — A template defines page capability. It establishes the initial structure, allowed authoring surface and page component. Speaker cue: a template is not merely a visual screenshot.
  2. Slide 2 — Template type is the technical foundation. It provides the starting structure used to create editable templates. Speaker cue: developers maintain the type; template authors configure the template.
  3. Slide 3 — Structure is shared. Locked or shared elements update consistently across pages using the template. Speaker cue: navigation or global containers often belong here.
  4. Slide 4 — Initial content is copied once. It helps authors start but does not keep existing pages synchronized. Speaker cue: changing initial content is not a migration strategy.
  5. Slide 5 — Page content belongs to each page. Authors control local component instances within policy boundaries. Speaker cue: classify by who changes it and how often.

Demo: compare WKND template structure with initial content. Assignment: classify elements for the new Guide Page. Acceptance: every element is placed according to its lifecycle.

Day 7 · Policies and Style System

Retrieval question: A component is installed but unavailable in the editor. What should you inspect first?

  1. Slide 1 — Policy configures capability by context. It controls what authors can use without changing component code. Speaker cue: policy is a product decision expressed as configuration.
  2. Slide 2 — Allowed Components protect consistency. A missing component selector entry is commonly a policy issue, not a rendering defect. Speaker cue: demonstrate the before and after.
  3. Slide 3 — Design properties provide defaults. They let template owners control behavior across many component instances. Speaker cue: avoid duplicating defaults in every dialog.
  4. Slide 4 — Style System exposes semantic choices. Author-facing labels map controlled options to CSS classes. Speaker cue: use “Featured” rather than “Red background.”
  5. Slide 5 — Fewer meaningful choices are safer. Governance reduces inconsistent content and support cost. Speaker cue: every option becomes a state that must be tested.

Demo: enable a WKND component and style through policy. Assignment: design three semantic Guide Card styles. Acceptance: names describe intent and all states are testable.

Day 8 · Dialogs and persistence

Retrieval question: What does a dialog field named ./title create?

  1. Slide 1 — A dialog is an authoring contract. It collects only the information required to express the component's intent. Speaker cue: every field creates authoring and compatibility cost.
  2. Slide 2 — Granite UI describes the interface. Dialog fields are resources composed from reusable UI components. Speaker cue: inspect a WKND dialog definition in source.
  3. Slide 3 — Field names define persistence. A relative name such as ./title stores a property on the component resource. Speaker cue: trace field → property → render.
  4. Slide 4 — Validation guides authors. Required fields, descriptions and useful constraints prevent avoidable invalid states. Speaker cue: server-side code still treats stored content as untrusted.
  5. Slide 5 — New code must tolerate old content. Missing or legacy properties need explicit fallbacks. Speaker cue: deployments update code before every page is re-authored.

Demo: follow a WKND field from dialog to JCR and HTL. Assignment: implement the Guide Card dialog contract. Acceptance: labels, stored names, validation and fallback behavior agree.

Day 9 · Assets and accessible images

Retrieval question: When should an image have an empty alternative text value?

  1. Slide 1 — DAM assets are managed content. AEM Assets stores binaries plus metadata, references and processing results. Speaker cue: do not treat DAM as a static public folder.
  2. Slide 2 — Use the Core Image capability. It provides responsive delivery and authoring behavior that custom markup would need to rebuild. Speaker cue: extend only for a verified gap.
  3. Slide 3 — Context determines alternative text. Informative images need meaning; decorative images need an empty alternative. Speaker cue: file names are not descriptions.
  4. Slide 4 — Responsive images reduce waste. The browser should receive an appropriate rendition for viewport and density. Speaker cue: visual dimensions alone do not reduce downloaded bytes.
  5. Slide 5 — References affect maintenance. Moving, publishing or replacing an asset can affect many pages. Speaker cue: inspect references before destructive changes.

Demo: author a WKND image and inspect responsive markup. Assignment: prepare three Guide assets and classify their alternative text. Acceptance: metadata and rendered behavior match image purpose.

Day 10 · Authoring checkpoint

Retrieval question: Name one requirement that belongs in a template, one in a policy and one in a component.

  1. Slide 1 — Start with the author outcome. An author must create a valid Guide Page without developer intervention. Speaker cue: evaluate the task, not whether the screen looks familiar.
  2. Slide 2 — Inspect lifecycle boundaries. Shared structure, configurable policy and local content must be intentionally separated. Speaker cue: wrong ownership becomes maintenance debt.
  3. Slide 3 — Test the empty path. New pages and unconfigured components must guide rather than fail. Speaker cue: the first author experience is an acceptance case.
  4. Slide 4 — Review accessibility at author time. Dialog guidance should make the accessible choice the easiest choice. Speaker cue: production audits are too late to fix every content instance.
  5. Slide 5 — Evidence closes the checkpoint. Show the template, policy path, authored result and one improvement from review. Speaker cue: an explanation without an artifact is not completion.

Demo: review one Guide Page against the rubric. Assignment: asynchronously review another contributor's authoring slice and apply one fix. Acceptance: two evidence-based findings and one verified correction.

Week 3 · Frontend development in AEM

Day 11 · Safe and readable HTL

Retrieval question: Which layer should prepare data, and which layer should render it?

  1. Slide 1 — HTL is the view layer. It renders prepared values into HTML and should not contain business orchestration. Speaker cue: complex logic belongs in a Sling Model or service.
  2. Slide 2 — Expressions read values. Use concise expressions for properties and model getters; keep naming meaningful to the markup. Speaker cue: readable templates are easier to review for security.
  3. Slide 3 — Conditions and lists express structure. data-sly-test and data-sly-list control output without Java scriptlets. Speaker cue: always define the empty state.
  4. Slide 4 — Templates and calls prevent repetition. Reuse small markup patterns while preserving clear inputs. Speaker cue: do not create a private framework inside HTL.
  5. Slide 5 — Output context is a security control. HTML, attribute, URI and script contexts require different handling; HTL applies context-aware escaping. Speaker cue: explicit context is required when automatic inference is impossible.

Demo: render Guide Card properties, condition and empty state. Assignment: create safe HTL for configured and missing data. Acceptance: valid markup, no business logic and correct output contexts.

Day 12 · Client Libraries and frontend workflow

Retrieval question: Why can a CSS source change exist in Git but not appear in the browser?

  1. Slide 1 — Clientlibs package browser assets. Categories identify CSS and JavaScript that AEM can include on a page. Speaker cue: category names are the runtime contract.
  2. Slide 2 — Source and generated output differ. WKND frontend source is compiled and embedded into AEM clientlibs during Maven build. Speaker cue: do not edit generated clientlib output.
  3. Slide 3 — Dependencies and embeds serve different goals. Dependencies load another category; embeds combine content into the current clientlib. Speaker cue: careless graphs create duplicates and ordering bugs.
  4. Slide 4 — Scope assets deliberately. Site-level assets belong in the site bundle; component behavior should remain small and isolated. Speaker cue: global CSS is a shared production dependency.
  5. Slide 5 — Debug the delivered result. Inspect page source, network requests, generated files and browser console before changing configuration. Speaker cue: verify which artifact the browser actually received.

Demo: change WKND frontend source, build and find the resulting clientlib request. Assignment: add Guide Card styling through the existing pipeline. Acceptance: source is versioned, generated output is not and the browser receives one intended asset.

Day 13 · Core Components and the proxy pattern

Retrieval question: What is lost when product component code is copied into the project?

  1. Slide 1 — Core Components are production capabilities. They provide tested authoring, markup, accessibility and versioned behavior. Speaker cue: begin every component request by checking existing capability.
  2. Slide 2 — A proxy gives the site ownership. The project defines its own resource type, title, group and policy surface. Speaker cue: authors see the project component, not the product path.
  3. Slide 3 — The super type delegates implementation. sling:resourceSuperType reuses the Core Component without copying it. Speaker cue: inherited behavior can receive product fixes.
  4. Slide 4 — Customize at the narrowest extension point. Policy, style, dialog extension, model delegation or markup override have different costs. Speaker cue: choose the first point that meets the requirement.
  5. Slide 5 — Version compatibility is explicit. A proxy must target a supported Core Component version and preserve existing authored content. Speaker cue: an upgrade is a tested change, not a string replacement.

Demo: inspect a WKND proxy and its super type. Assignment: implement the Guide Card with the smallest viable extension. Acceptance: no copied product implementation and the customization decision is justified.

Day 14 · Responsive, accessible and empty states

Retrieval question: Which component state is visible to an author before any content is configured?

  1. Slide 1 — Responsive means behavior, not screenshots. Content and controls must remain usable across width, zoom and long text. Speaker cue: test at boundaries, not only three device presets.
  2. Slide 2 — Native semantics come first. Correct headings, links, buttons and landmarks provide behavior before ARIA is added. Speaker cue: ARIA cannot repair the wrong interaction model.
  3. Slide 3 — Keyboard operation is required. Focus order, visible focus and activation must work without a pointer. Speaker cue: perform the demo without touching the mouse.
  4. Slide 4 — Empty states serve two audiences. Authors need guidance in edit mode; visitors should not receive broken or meaningless markup. Speaker cue: author placeholders must not leak to Publish.
  5. Slide 5 — Test content extremes. Missing, long, localized and unexpected values reveal assumptions earlier than the happy path. Speaker cue: use real text, not repeated lorem ipsum.

Demo: test Guide Card with keyboard, narrow viewport and no content. Assignment: record and fix the highest-risk failure. Acceptance: keyboard, 200% zoom, long title and empty state pass.

Day 15 · Vertical frontend ticket

Retrieval question: What evidence proves that a component is authorable, not only renderable?

  1. Slide 1 — Start with observable acceptance. Describe what an author configures and what a visitor receives. Speaker cue: file changes are implementation, not the outcome.
  2. Slide 2 — Trace the full slice. Policy → dialog → stored property → model/value → HTL → clientlib. Speaker cue: every broken handoff produces a different symptom.
  3. Slide 3 — Reuse before customization. Confirm Core Component, WKND pattern and existing utility options before adding code. Speaker cue: a smaller diff is easier to maintain and test.
  4. Slide 4 — Prove important states. Configured, empty, long content, responsive and keyboard states belong in the ticket. Speaker cue: acceptance criteria choose tests.
  5. Slide 5 — Present the decision, not a file tour. Explain the selected extension point, rejected alternative and remaining risk. Speaker cue: reviewers can inspect files after understanding intent.

Demo: decompose one Guide Card story into the vertical trace. Assignment: complete the frontend slice and open a PR. Acceptance: author and visitor evidence, state checks and a concise design explanation.

Week 4 · Essential backend development

Day 16 · Java and OSGi inside AEM

Retrieval question: What turns compiled Java classes into an active capability inside AEM?

  1. Slide 1 — An OSGi bundle is a managed JAR. Metadata declares exported packages, imports and runtime identity. Speaker cue: successful compilation does not guarantee resolved runtime dependencies.
  2. Slide 2 — OSGi creates components. Declarative Services manages lifecycle, activation and references; application code should not manually instantiate them. Speaker cue: the container provides collaboration.
  3. Slide 3 — Services publish contracts. Consumers depend on a focused capability rather than a concrete implementation. Speaker cue: do not create an interface when there is no useful boundary.
  4. Slide 4 — Runtime state is diagnostic evidence. Active, satisfied, resolved and installed states point to different dependency problems. Speaker cue: inspect state before reinstalling the same package.
  5. Slide 5 — Cloud instances are replaceable. Durable state must not depend on local memory or filesystem. Speaker cue: design every service for restart and multiple instances.

Demo: locate a WKND class, its bundle and component state. Assignment: map three project classes to runtime responsibilities. Acceptance: bundle, component/service role and lifecycle are correct.

Day 17 · Sling Models

Retrieval question: When should a model adapt from a resource rather than a request?

  1. Slide 1 — The adaptable defines available context. A resource model is portable; a request model is appropriate when request-specific objects are required. Speaker cue: choose the narrowest context.
  2. Slide 2 — Injection maps AEM data. Properties, child resources and services can be injected with explicit optionality. Speaker cue: invisible injection failure becomes an empty page.
  3. Slide 3 — The model is a view contract. Getters expose values already prepared for HTL. Speaker cue: HTL should not know repository fallbacks or formatting rules.
  4. Slide 4 — Fallbacks protect legacy content. Missing properties must produce safe behavior rather than exceptions. Speaker cue: deploy code without assuming every component was re-authored.
  5. Slide 5 — Services own reusable orchestration. Large queries, integrations or shared logic do not belong in getters. Speaker cue: a model coordinates the view; it is not the entire application.

Demo: implement a Guide title with a fallback. Assignment: connect a Sling Model to Guide Card HTL. Acceptance: configured, missing and legacy values render without exceptions.

Day 18 · OSGi services and configuration

Retrieval question: Which values may vary by environment without changing application code?

  1. Slide 1 — Create a service for reusable behavior. A service should have one capability needed by a real consumer. Speaker cue: avoid a service layer that only forwards a getter.
  2. Slide 2 — Typed configuration documents the contract. Metatype names properties, types, descriptions and safe defaults. Speaker cue: configuration is an operational API.
  3. Slide 3 — Run modes select environment values. Author/Publish and dev/stage/prod configurations remain separate from Java conditionals. Speaker cue: inspect the effective value, not only the source file.
  4. Slide 4 — Secrets do not belong in Git. Use approved secret environment configuration and never expose values in logs or screenshots. Speaker cue: a placeholder name can be versioned; the secret cannot.
  5. Slide 5 — Missing configuration fails safely. Choose a secure fallback or disable the capability with a useful diagnostic. Speaker cue: silent partial behavior is hard to operate.

Demo: configure a Guide URL service with a non-secret base path. Assignment: implement typed configuration and a safe fallback. Acceptance: environment variation requires no hardcoded conditional and no secret reaches Git.

Day 19 · Resource API and servlets

Retrieval question: What existing AEM capability could eliminate the need for a new endpoint?

  1. Slide 1 — Prefer the Resource API for content. It expresses paths, properties and children without unnecessary JCR coupling. Speaker cue: use JCR APIs only for JCR-specific requirements.
  2. Slide 2 — Respect resolver ownership. Close resolvers created by your service; never close a resolver received from a request or model. Speaker cue: leaks and premature closes both become production faults.
  3. Slide 3 — Resource-type servlets bind to domain resources. They avoid global path endpoints and participate in Sling resolution. Speaker cue: a path servlet expands unaudited public surface.
  4. Slide 4 — Every endpoint is a trust boundary. Validate method, input, permissions, response type and caching behavior. Speaker cue: “internal” URLs still receive untrusted requests.
  5. Slide 5 — The best servlet may be no servlet. A model, Core Component or existing JSON exporter can meet many requirements with less code and risk. Speaker cue: require evidence for adding a new API.

Demo: compare model and servlet solutions for Guide List. Assignment: decide the minimum solution for three cases. Acceptance: each decision names capability, security surface and reason.

Day 20 · Unit testing Sling Models and services

Retrieval question: What behavior should fail if the fallback implementation is removed?

  1. Slide 1 — Test observable behavior. Inputs, outputs and fallbacks matter more than private methods or injection mechanics. Speaker cue: a refactor should not rewrite every test.
  2. Slide 2 — AEM Mocks provides a small runtime model. Load only the resources, models and services required by the behavior. Speaker cue: avoid copying a production repository into a unit test.
  3. Slide 3 — Arrange the smallest meaningful content. JSON fixtures should reveal the scenario and remain easy to review. Speaker cue: large fixtures hide which property matters.
  4. Slide 4 — Act once and assert the contract. Adapt the model or call the service, then check the values a consumer sees. Speaker cue: assertions should explain the requirement.
  5. Slide 5 — A regression test must detect the defect. Confirm it fails before the fix or under an equivalent mutation. Speaker cue: a permanently green test can prove nothing.

Demo: red test → minimal implementation → green test for Guide Card. Assignment: test configured, missing and invalid input. Acceptance: focused tests pass and at least one is proven to detect the missing behavior.

Week 5 · Maintenance and investigation

Day 21 · Cloud-compatible project structure

Retrieval question: Which repository paths may change operationally, and which are deployed as immutable code?

  1. Slide 1 — Application code is immutable. /apps and product code are replaced through deployment, not edited on a cloud runtime. Speaker cue: CRXDE inspection is diagnostic, not a production development workflow.
  2. Slide 2 — Managed content is mutable. /content and /conf can evolve through authoring and administration. Speaker cue: package installation must preserve those changes.
  3. Slide 3 — Packages have explicit responsibilities. Code, configuration and sample content should not be mixed behind broad filters. Speaker cue: package boundaries express update behavior.
  4. Slide 4 — The all package composes deployables. Cloud Manager installs one container that embeds the required subpackages. Speaker cue: inspect embedded package types and dependencies.
  5. Slide 5 — Filters can destroy content. A broad replace filter may overwrite author changes; WKND sample content should use merge behavior for the lab. Speaker cue: test a second deployment after authoring.

Demo: trace WKND packages inside all and inspect sample-content filters. Assignment: classify ten paths and make sample deployment safe. Acceptance: rebuild does not overwrite authored Guide content.

Day 22 · Runtime diagnostic tools

Retrieval question: Which runtime view would you inspect for an unsatisfied service reference?

  1. Slide 1 — Logs provide a timed execution record. Narrow by service, request, correlation detail and root exception. Speaker cue: the first cause is often above the final summary.
  2. Slide 2 — Bundle state reveals package resolution. Installed or resolved bundles may have missing imports even when Maven passed. Speaker cue: compare symbolic name, version and imported package.
  3. Slide 3 — Components reveal service satisfaction. Inspect activation state and required references before changing annotations. Speaker cue: one inactive dependency can cascade to many consumers.
  4. Slide 4 — Effective configuration beats assumptions. Confirm the active PID, values and run mode on the affected service. Speaker cue: the committed file may not be the selected configuration.
  5. Slide 5 — Repository tools are read-first diagnostics. Use Repository Browser or CRXDE to confirm content and paths, not to create untracked fixes. Speaker cue: the durable fix belongs in Git or authoring workflow.

Demo: diagnose an inactive Guide service caused by a missing reference. Assignment: resolve a seeded runtime failure. Acceptance: exact evidence, cause, source fix and verification are recorded.

Day 23 · Workflows, launchers and jobs

Retrieval question: Which mechanism represents a business process with visible steps and state?

  1. Slide 1 — A workflow models a managed process. It has a payload, steps, participants and observable state. Speaker cue: do not use a workflow merely to run arbitrary background code.
  2. Slide 2 — A launcher reacts to repository events. Paths, node types, event types and exclusions must be narrow. Speaker cue: broad launchers create event storms and duplicate work.
  3. Slide 3 — A job represents asynchronous work. It can be queued, retried and processed by an appropriate instance. Speaker cue: manually creating threads is not cloud-safe scheduling.
  4. Slide 4 — Idempotency makes retries safe. Processing the same payload twice must not duplicate destructive side effects. Speaker cue: define the stable key and completed state.
  5. Slide 5 — Cloud execution is distributed. Code must tolerate multiple instances, restarts and delayed processing. Speaker cue: local memory cannot coordinate a cluster.

Demo: trace event → launcher → workflow/job for a Guide Page. Assignment: review filters, permissions and retry behavior. Acceptance: duplicate risk and idempotency strategy are explicit.

Day 24 · Search and indexes

Retrieval question: Why is a repository traversal warning a design signal rather than harmless noise?

  1. Slide 1 — A query should express a narrow intent. Path, primary type and required properties reduce the search space. Speaker cue: a broad query makes every future content increase more expensive.
  2. Slide 2 — Traversal does not scale. Reading many nodes to return a few results consumes shared runtime resources. Speaker cue: small local content can hide the problem.
  3. Slide 3 — Indexes serve real query shapes. Add or change an index only from measured queries and requirements. Speaker cue: one index per developer intuition creates cost without benefit.
  4. Slide 4 — Explain shows the selected plan. Verify which index or traversal the repository will use before claiming optimization. Speaker cue: evidence is the plan, not only faster local timing.
  5. Slide 5 — Cloud indexes deploy as coordinated code. Definitions and query changes must be versioned and rolled out safely. Speaker cue: index work is a deployment decision, not an author fix.

Demo: compare an unbounded query with a path/type-constrained Guide query. Assignment: implement Guide List and capture explain output. Acceptance: no traversal and the query returns only intended pages.

Day 25 · Maintenance simulation

Retrieval question: What information in a bug report describes the symptom but not the cause?

  1. Slide 1 — The ticket is not the diagnosis. User language identifies impact; it does not identify the failing layer. Speaker cue: preserve the report while testing its assumptions.
  2. Slide 2 — Build a minimal reproduction. Remove variables until one controlled case consistently shows the failure. Speaker cue: a reliable small failure is faster than random changes.
  3. Slide 3 — Trace every caller before fixing. A shared helper, policy or service may cause multiple visible symptoms. Speaker cue: fix once at the common source.
  4. Slide 4 — Leave a regression check. The smallest test or repeatable check must fail when the defect returns. Speaker cue: a fix without a check becomes tribal memory.
  5. Slide 5 — Communicate operationally. State cause, change, evidence and remaining risk in language another maintainer can act on. Speaker cue: five precise lines beat a chronological diary.

Demo: investigate a misleading WKND Guide symptom. Assignment: resolve a timed individual maintenance ticket. Acceptance: root-cause fix, regression proof and concise incident note.

Week 6 · Cloud delivery

Day 26 · Programs, environments and Git

Retrieval question: Which artifact should move from validation toward production without manual rebuilding?

  1. Slide 1 — A Cloud Manager program groups delivery. It contains repositories, environments and pipelines for an initiative. Speaker cue: distinguish the Adobe organization from the program.
  2. Slide 2 — Environments contain separate services. Development, Stage and Production provide Author and Publish tiers with different purposes. Speaker cue: configuration varies; source intent should not.
  3. Slide 3 — Git is the deployable source of truth. A pipeline builds a selected branch from a configured repository. Speaker cue: runtime edits cannot replace a committed fix.
  4. Slide 4 — Small PRs reduce delivery risk. One coherent outcome is easier to review, test and diagnose. Speaker cue: rollback is conceptual in an immutable deployment model.
  5. Slide 5 — Promote the validated artifact. Stage and Production should receive what passed earlier gates, not handcrafted differences. Speaker cue: rebuild drift undermines evidence.

Demo: trace a WKND commit to Development using real access or an anonymized example. Assignment: diagram the team's actual flow. Acceptance: owners, repository, branch, gates, services and environments are named.

Day 27 · Cloud Manager pipelines and quality gates

Retrieval question: Where should you start reading a failed pipeline log?

  1. Slide 1 — A full-stack pipeline builds and deploys. It compiles, tests, analyzes, packages and releases application code and configuration. Speaker cue: pipeline stages create different types of evidence.
  2. Slide 2 — Builds start clean. Cloud containers cannot rely on a developer's local cache, file or unpublished dependency. Speaker cue: reproducibility is a feature of the project.
  3. Slide 3 — Quality gates stop known risk. Code quality, security, performance and compatibility findings can block progression. Speaker cue: do not bypass a gate before understanding its protected outcome.
  4. Slide 4 — The first actionable error matters. Final “build failed” lines summarize; the originating compiler, test or analyzer message explains. Speaker cue: read upward to the earliest relevant cause.
  5. Slide 5 — Assign the correct owner. Source, dependency, test, Dispatcher and platform failures require different next actions. Speaker cue: retry is only valid for a verified transient condition.

Demo: annotate a failed WKND pipeline log. Assignment: classify three failures and propose the next check. Acceptance: stage, first error, owner and action are correct.

Day 28 · Dispatcher fundamentals

Retrieval question: Which Dispatcher concern decides whether a request is allowed to reach Publish?

  1. Slide 1 — Dispatcher is a reverse proxy and cache. It protects and accelerates Publish but does not replace application authorization. Speaker cue: separate delivery controls from content permissions.
  2. Slide 2 — Filters restrict request surface. Deny by default, then allow only required methods, paths, selectors and extensions. Speaker cue: broad allow rules become public attack surface.
  3. Slide 3 — Virtual hosts select site configuration. Host and URL rules connect an incoming request to rewrites, filters and cache behavior. Speaker cue: test the intended host, not only localhost.
  4. Slide 4 — Rewrites normalize URLs. They can change public paths but should not hide broken content architecture. Speaker cue: trace both external and internal URL.
  5. Slide 5 — Cache only safe shared responses. Public stable GET responses are candidates; personalized or mutable operations are not. Speaker cue: “faster” is not a sufficient caching rule.

Demo: evaluate a Guide URL against vhost, filter and cache rules. Assignment: classify ten requests. Acceptance: each decision cites the exact rule and risk.

Day 29 · CDN, headers and invalidation

Retrieval question: How can two cache layers make a stale-content incident harder to locate?

  1. Slide 1 — CDN and Dispatcher are separate caches. Either layer may answer without reaching Publish. Speaker cue: include browser cache as a third observation point, not part of Dispatcher.
  2. Slide 2 — A miss moves inward. The request continues until a layer can produce a response, then caches may store it. Speaker cue: first-request latency can reveal this path.
  3. Slide 3 — Headers express freshness and sharing. Inspect effective response headers rather than inferring configuration from symptoms. Speaker cue: capture the same URL under controlled conditions.
  4. Slide 4 — Publication and invalidation interact. Published content can invalidate cached resources, but dynamic dependencies require deliberate rules. Speaker cue: one page can depend on content stored elsewhere.
  5. Slide 5 — Compare repeatable requests. Status, age, cache indicators, timing and content version help identify the answering layer. Speaker cue: record evidence before clearing every cache.

Demo: compare two requests and a publication event. Assignment: diagnose hit/miss behavior for Guide pages. Acceptance: evidence distinguishes browser, CDN, Dispatcher and Publish.

Day 30 · Deployment rehearsal

Retrieval question: Which two user journeys should a post-deployment smoke test include?

  1. Slide 1 — Preflight removes cheap failures. Run clean build, focused tests, diff review and configuration checks before starting a pipeline. Speaker cue: a cloud pipeline is not a substitute for local feedback.
  2. Slide 2 — Observe each deployment stage. Record commit and stage transitions rather than repeatedly refreshing the final status. Speaker cue: evidence must connect the artifact to the environment.
  3. Slide 3 — Smoke test author and visitor paths. Confirm one critical authoring action and one Publish request after deployment. Speaker cue: build success alone does not prove runtime behavior.
  4. Slide 4 — Preserve failure evidence before retrying. Save the stage, first error, log and commit. Speaker cue: a retry can erase the easiest reproduction.
  5. Slide 5 — A runbook transfers operation. Another developer should be able to execute checks and know the first response to failure. Speaker cue: keep steps short, ordered and testable.

Demo: execute a real pipeline or an anonymized rehearsal. Assignment: run and improve the deployment checklist. Acceptance: every gate has evidence and another contributor can follow the runbook.

Week 7 · Production quality

Day 31 · Permissions and service users

Retrieval question: Why should a backend service never use an administrator session?

  1. Slide 1 — Principals receive privileges. Users, groups and service users are granted actions on defined repository paths. Speaker cue: separate identity from what the identity may do.
  2. Slide 2 — Least privilege limits impact. Grant only required paths and actions for the actual capability. Speaker cue: “read everything” is not a convenient default.
  3. Slide 3 — Groups make human access maintainable. Assign users to role-based groups instead of managing many individual ACLs. Speaker cue: onboarding and removal should be predictable.
  4. Slide 4 — Service users identify backend code. Resource resolver mappings provide bounded access without human or administrator credentials. Speaker cue: credentials in code are both insecure and inoperable.
  5. Slide 5 — Repo Init makes access reviewable. Versioned principal and ACL definitions can be tested and promoted with code. Speaker cue: verify the resulting permissions, not only script syntax.

Demo: read a Guide access matrix and resolver mapping. Assignment: define access for authors and the Guide service. Acceptance: no admin, wildcard or hardcoded credential; each privilege has a requirement.

Day 32 · Component and endpoint security

Retrieval question: Which inputs reach AEM from an untrusted boundary?

  1. Slide 1 — Treat content and requests as untrusted. Dialog values, URL parameters, headers and external responses require limits. Speaker cue: authenticated authors can still store unsafe or unexpected data.
  2. Slide 2 — Encode output for its destination. HTML text, attributes, URIs and script contexts require different protections. Speaker cue: use HTL context-aware escaping rather than manual string replacement.
  3. Slide 3 — Mutating operations need method and CSRF controls. A GET must not change state and authenticated requests still need forgery protection. Speaker cue: browser convenience is not an API design.
  4. Slide 4 — Secrets stay outside repository and response. Approved secret configuration must not appear in Git, logs or rendered markup. Speaker cue: redact diagnostic evidence before sharing.
  5. Slide 5 — Dispatcher reduces exposed surface. Block internal paths, unsafe selectors and methods that public Publish does not need. Speaker cue: defense in depth complements application checks.

Demo: threat-review the proposed Guide endpoint. Assignment: identify assets, entry points and controls for Guide Card/List. Acceptance: three concrete risks, each with an observable control.

Day 33 · Accessibility and SEO

Retrieval question: Which quality checks require human judgment even when automated tools pass?

  1. Slide 1 — Semantic HTML creates the document model. Headings, landmarks, links and buttons must describe meaning and interaction. Speaker cue: begin with native elements before ARIA.
  2. Slide 2 — Authoring can prevent inaccessible content. Dialog labels, guidance and safe defaults make required metadata easier to supply. Speaker cue: quality is partly a component design responsibility.
  3. Slide 3 — Keyboard and focus reveal interaction defects. Order, visibility and activation must remain usable without a pointer. Speaker cue: demonstrate the complete Guide Card journey by keyboard.
  4. Slide 4 — Page metadata supports discovery. Title, description, canonical URL and heading structure must describe the Guide Page consistently. Speaker cue: inspect rendered output, not only dialog fields.
  5. Slide 5 — Automation is partial evidence. Scanners find rule violations; people confirm purpose, reading order and useful alternatives. Speaker cue: combine tool results with a short manual protocol.

Demo: audit one Guide Page with browser tools and keyboard. Assignment: fix one accessibility and one SEO finding. Acceptance: reproducible before/after evidence and no regression in authoring.

Day 34 · Performance and test strategy

Retrieval question: What is the cheapest test that detects the risk you are discussing?

  1. Slide 1 — Measure before optimizing. Use the same URL, content, cache state and environment for baseline and comparison. Speaker cue: intuition identifies a question, not the answer.
  2. Slide 2 — Frontend cost includes bytes and work. Asset size, request count, rendering and responsive behavior affect visitor experience. Speaker cue: a visually small image can still be a large download.
  3. Slide 3 — Backend cost happens per request or job. Queries, remote calls and repeated model work can multiply under traffic. Speaker cue: identify execution frequency before micro-optimizing code.
  4. Slide 4 — Shared caching is often the largest lever. A safe cache hit removes work across the entire request path. Speaker cue: performance never overrides privacy or correctness.
  5. Slide 5 — Match the test to the failure. Unit, integration, UI and smoke checks have different speed and confidence. Speaker cue: use the lowest-cost test that observes the real risk.

Demo: select tests for five Guide failures. Assignment: build a risk-to-test matrix and improve one measured issue. Acceptance: baseline, change and equivalent after measurement are supplied.

Day 35 · Production-readiness review

Retrieval question: What can pass functional testing but still make a component unsafe for production?

  1. Slide 1 — Verify behavior and states. Acceptance, empty, error and regression paths must be observable. Speaker cue: “works on my page” is one state, not readiness.
  2. Slide 2 — Verify authorability. Labels, defaults, policies and existing content must support maintainable use. Speaker cue: count the decisions imposed on an author.
  3. Slide 3 — Verify maintainability. Reuse, module location, focused dependencies and a small diff reduce future work. Speaker cue: compare with the closest WKND pattern.
  4. Slide 4 — Verify security and performance. Inputs, output contexts, permissions, queries, assets and caching need evidence. Speaker cue: prioritize data/security before visual polish.
  5. Slide 5 — Verify operability. Logs, tests, deployment checks and first-response guidance let another person maintain the feature. Speaker cue: production ownership starts before release.

Demo: review one Guide PR with the five lenses. Assignment: asynchronously review another contributor's PR. Acceptance: one actionable evidence-based finding and one accepted verified correction.

Week 8 · Capstone and transfer

Day 36 · Plan the final increment

Retrieval question: What outcome can one contributor deliver and demonstrate independently?

  1. Slide 1 — Start from user outcome. Describe what an author or visitor can do when the increment is complete. Speaker cue: avoid backlog items named only after modules.
  2. Slide 2 — Slice vertically. A ticket should reach observable behavior through the required layers. Speaker cue: horizontal “all dialogs” work delays feedback.
  3. Slide 3 — Preserve individual ownership. One contributor must explain, modify and verify each item even when reviews are collaborative. Speaker cue: group output cannot hide individual gaps.
  4. Slide 4 — Order real dependencies. Template, policy, model, frontend, configuration and deployment constraints shape sequence. Speaker cue: distinguish dependency from preferred order.
  5. Slide 5 — Write acceptance before implementation. Include happy path, empty state, security and evidence expectations. Speaker cue: acceptance defines the stopping point.

Demo: split a large Weekend Guides story into six slices. Assignment: refine the final backlog. Acceptance: six independently owned, testable tickets with explicit dependencies.

Day 37 · Implement the capstone

Retrieval question: Which existing WKND pattern is closest to your ticket?

  1. Slide 1 — Begin with the acceptance check. Write the test or repeatable checklist before the implementation changes. Speaker cue: this exposes missing assumptions early.
  2. Slide 2 — Choose the smallest path. Reuse WKND patterns and Core Components before creating new code. Speaker cue: familiarity for maintainers is a quality attribute.
  3. Slide 3 — Keep commits coherent. Each commit should express one reviewable intention and remain buildable when practical. Speaker cue: history is part of incident investigation.
  4. Slide 4 — Ask for feedback when behavior exists. Open a draft PR when the first vertical slice is observable. Speaker cue: early review of intent is cheaper than late review of polish.
  5. Slide 5 — Capture evidence while working. Preserve commands, tests and author/visitor results before context disappears. Speaker cue: do not reconstruct proof on demo day.

Demo: implement the instructor's first thin slice. Assignment: deliver the owned capstone ticket. Acceptance: draft PR shows working behavior, current checks and an explicit remaining task.

Day 38 · Hardening and defects

Retrieval question: Which boundary condition is most likely to invalidate your implementation assumption?

  1. Slide 1 — Cross-review challenges assumptions. The reviewer attempts to reproduce edge cases, not merely confirm style. Speaker cue: constructive review includes evidence and impact.
  2. Slide 2 — Test boundary states. Missing, long, unauthorized and dependency-failure scenarios reveal resilience. Speaker cue: choose boundaries relevant to the specific ticket.
  3. Slide 3 — Check neighboring behavior. Shared policies, services, CSS and cache rules can regress other pages. Speaker cue: trace consumers before declaring the fix local.
  4. Slide 4 — Prioritize by risk. Data and security, functional correctness, operability and polish are addressed in that order. Speaker cue: severity is impact times likelihood, not reviewer preference.
  5. Slide 5 — Resolve comments with proof. State what changed and which check now passes. Speaker cue: “done” without evidence moves uncertainty to the reviewer.

Demo: turn a vague comment into a reproducible finding. Assignment: review and harden one peer ticket. Acceptance: traceable review, prioritized fix and regression evidence.

Day 39 · Individual practical assessment

Retrieval question: What process will you follow before touching code in an unfamiliar ticket?

  1. Slide 1 — The case is new but the pattern is familiar. Assessment uses a variation of practiced work, not trivia. Speaker cue: success is transfer, not memorization.
  2. Slide 2 — Documentation is allowed; direct implementation help is not. Real developers consult authoritative sources while owning the decision. Speaker cue: record when and why a source was used.
  3. Slide 3 — The process is observable. Reproduce, locate, hypothesize, change and verify in a deliberate sequence. Speaker cue: a correct result with no explainable path is incomplete evidence.
  4. Slide 4 — Decisions require alternatives and risk. Explain why the selected approach is smaller or safer and what remains uncertain. Speaker cue: confidence must match evidence.
  5. Slide 5 — Use the common proficiency scale. Not demonstrated, with support, independent or can guide describes current evidence. Speaker cue: the level is per capability, not a permanent label.

Demo: explain assessment rules without revealing the solution. Assignment: complete a timed individual maintenance ticket. Acceptance: working behavior, relevant check and technical defense.

Day 40 · Demo, defense and the next 30 days

Retrieval question: What evidence best demonstrates the capability you improved most?

  1. Slide 1 — Demonstrate outcomes. Show the author task, visitor experience and evidence rather than navigating source folders. Speaker cue: begin from the acceptance criterion.
  2. Slide 2 — Defend the design. Explain the selected extension point, rejected alternative and known limit. Speaker cue: tradeoffs show understanding better than perfection claims.
  3. Slide 3 — Explain operation. Another maintainer needs deployment, observation and first diagnostic steps. Speaker cue: point to the tested runbook.
  4. Slide 4 — Retrospect on learning behavior. Identify which practice to keep, change or remove based on evidence. Speaker cue: separate course mechanics from individual capability.
  5. Slide 5 — Commit to one 30-day outcome. Each contributor chooses a real work goal and the evidence that will prove it. Speaker cue: a concrete artifact is stronger than “learn more AEM.”

Demo: present the completed Weekend Guides increment. Assignment: answer an assigned technical scenario and publish the 30-day goal. Acceptance: final proficiency is evidence-based and each next action is observable.
