Integrated practice: a Weekend Guides page

Build one working AEM page, trace how it obtains its content, and explain one correction. Three practice variants divide the course concepts. Each variant ends with a page and components that can be demonstrated.

How to participate: work individually or in pairs. With six participants, one pair can take each variant. The criteria below support self-checks and feedback; they are not a grade. The instructor can demonstrate the prepared example when participants prefer to observe.

Starting point and shared result

Everyone already has a working local AEM project and Author instance. Continue in that project; use its existing content root and components.

  1. Create a Weekend Guides page from an editable template. Its policy should allow Title, Image, and Container Core Components or their existing proxies.
  2. Build a header, an image with useful alternative text, an introduction, a guide area, and the section required by your variant. The final page must render authored content in Author.
  3. Check the page at a narrow and a wide viewport, navigate its interactive parts with a keyboard, and inspect the relevant Data Layer event if the existing components expose one.
  4. Keep the local page URL and a short trace: request → Sling resource → component/HTL/Model → JCR content or fragment → response. Mark observations separately from assumptions.

For feedback, show the page in your local instance. If you changed code or configuration, show the relevant file, installation or test command, and result. Screenshots or a short recording can replace a live demonstration.

Choose one practice variant

Every variant uses the shared page. A participant completes one variant; the group covers the broader course when the three results are reviewed together.

A · Reusable content and localization

  1. Model a guide: create or reuse a Content Fragment with a title, summary, and image reference. Add a tag. Configure a card or teaser through its dialog to select the fragment. Use HTL and a Sling Model only if the existing component cannot render the required fields.
  2. Reuse a section: place an Experience Fragment on the page as a shared editorial band. Explain why the band is reusable presentation and the Content Fragment is structured content.
  3. Localize: create a Live Copy or use an existing MSM relationship. Change text in the source, perform the available rollout, and show the inherited change. Cancel inheritance for one local property, add a visible override, and check that it survives the next applicable rollout.
  4. Check dependencies: if local Publish is available, publish the page, fragment, Experience Fragment, and asset, then inspect the result. For diagnosis, use this case: the fragment title is “New route” in Author but “Old route” in Publish because only the page was republished. Identify the first divergent resource and the next check.

Acceptance criteria A: the page displays the fragment-backed card and shared band; changing the fragment updates its Author consumer; the MSM demonstration shows an inherited change and a preserved override; the publication check identifies the missing dependency. The card remains usable by keyboard.

B · Components and backend behavior

  1. Build the section: create a guide card or status panel with its own resource type, a dialog for a guide path or identifier, escaped HTL output, and a useful empty state. Reuse Core Components for the standard page elements.
  2. Separate responsibilities: have a Sling Model read the component properties and call a small OSGi service for the displayed status. Explain which values belong in JCR and which, if any, belong in OSGi configuration.
  3. Expose a bounded check: if the status must be requested separately, add a GET servlet using a resource type or selector. Validate input, limit the response, and demonstrate a valid and invalid request. The servlet does not replace component rendering.
  4. Handle repeated work: reuse the retryable workflow/launcher and Sling Job exercise from earlier in the course. Trigger the same business key twice and show that the persisted effect occurs once. If using the local HTTP stub from the earlier retry exercise, set a timeout and handle its first 503 without blocking page rendering. Use a narrowly permitted subservice for technical writes; reads that must respect the visitor keep the visitor's identity.

Acceptance criteria B: changing the dialog changes the visible section; its empty state is readable; the Model, service, and JCR have clear roles; the servlet handles valid and invalid input; replay does not duplicate the effect. One JUnit/AEM Mocks negative test and one local HTTP or permission check cover the relevant risks.

C · Bounded queries, local delivery, and testable page behavior

  1. List guides: reuse Guide List or create a small list component. Query by content root, resource type, and tag with an explicit result limit. Show at least two included guides and one excluded guide. Inspect Explain/Measure and justify the query or existing index.
  2. Follow local delivery: publish the page and its content dependencies. Compare the response from Publish with the response through Dispatcher. Identify the relevant vhost/filter rule, one allowed and one blocked request, a cache miss and hit, and the result after a controlled content update. If Dispatcher is unavailable locally, use the instructor's HTTP trace and label those observations as supplied evidence.
  3. Test Java behavior: if the list contains project-owned Java logic, add a negative JUnit test for its filtering or limit and run JaCoCo. Otherwise, run the project's existing Java tests and inspect the JaCoCo report. Use coverage to find an untested branch, not as a score to chase.
  4. Test browser behavior: if the page has custom clientlib JavaScript, use Jest to test one visible behavior and its empty or invalid state. Use Cypress, as practiced in Week 10, to load the page from the running local AEM instance and verify authored content, included guides, and an excluded guide. Use the tools that match the code actually present.
  5. Check quality: inspect keyboard focus, image alt text, page title, and relevant metadata. Measure one query, image, or clientlib issue under comparable conditions, make one focused correction, and repeat the same check on the final page.

Acceptance criteria C: the tag-based list returns the intended included and excluded results within its limit, with a recorded query plan or measurement; Publish and Dispatcher responses identify the first divergent layer, including an allowed/blocked request and cache behavior demonstrated locally or in the supplied trace; at least one relevant automated negative test runs, and a Cypress integration check runs against local AEM when the Week 10 setup is available. A quality finding has a repeatable before/after check, and the final page remains usable by keyboard.

What to show for feedback

  • The final page in Author and, where available, local Publish/Dispatcher; the component names and where their content comes from.
  • One working case and one failure or excluded case, with enough local evidence to reproduce them.
  • The variant's correction or decision, its regression check, and one limit of the evidence.

Keep credentials, tokens, and private URLs out of screenshots. If a local layer is unavailable, state which check you would run there rather than presenting an assumption as an observed result.
