Class 2 · Week 1 · Day 2

Know where a change belongs.

Connect the local SDK, Maven reactor and WKND modules before editing implementation files.

  • 30 minutes online
  • 60–90 minutes practice
  • Individual evidence
Observable outcome: each contributor can explain the local development system, route a change to the correct WKND module and distinguish build validation from installation and runtime verification.

Architect preparation

  • Confirm that local Author is available or prepare a recorded fallback.
  • Open the team repository README and use its approved build and install commands.
  • Open the root pom.xml and the core, ui.apps, ui.content, ui.config, dispatcher and all modules.
  • Start from a clean working tree or a disposable training branch.

Learning objectives

By the end of the session, each contributor can:

  • distinguish the WKND source project, AEM SDK and Dispatcher Tools;
  • explain the root POM and Maven reactor at a practical level;
  • map common changes to the module that owns their lifecycle;
  • separate build, installation and functional evidence.

Worked example · live only if available

  1. From the repository root, open pom.xml and read the module list.
  2. Run the repository-approved validation command; use mvn clean verify only when it matches the README.
  3. Read the reactor summary from top to bottom and identify each module result.
  4. Locate the package produced by all under its target directory.
  5. Use the approved install profile and confirm the package on local Author.
  6. Open one WKND page or component and distinguish installation evidence from functional evidence.

If the build cannot download dependencies, preserve the exact command and error. Use a previously captured successful reactor output to teach the flow; do not hide the environment blocker.

Asynchronous assignment · Route before editing

Individual work, 60–90 minutes. For each scenario, choose the owning module, cite one representative path and state the evidence that would prove the change reached local AEM.

  1. Add a getter to an existing Sling Model.
  2. Add an authorable subtitle field and render it in HTL.
  3. Add project-managed starter content for a new training page.
  4. Configure a service endpoint differently for Author and Publish.
  5. Allow one additional public request path through Dispatcher.
  6. Locate the complete application package after a build.
Instructor feedback guide
  1. core; Java source path; unit/build evidence.
  2. ui.apps; dialog and HTL paths; authored and rendered evidence.
  3. ui.content; content package path; installed repository evidence.
  4. ui.config; run-mode configuration path; runtime configuration evidence.
  5. dispatcher; filter configuration path; validated request evidence.
  6. all; target package; successful reactor and artifact evidence.

Individual evidence

  1. The exact build command and final reactor summary.
  2. A repository map with the six scenarios routed to modules.
  3. One sentence per route explaining lifecycle or ownership.
  4. Local Author status, or the exact blocked step and error.

Acceptance criteria: the build reports BUILD SUCCESS and at least five of six module choices are correct and justified. Installation and page behavior must be reported as separate evidence.
