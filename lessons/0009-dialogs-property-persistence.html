Class 8 · Week 2 · Day 8 · August 26, 2026

Dialogs, Granite UI and property persistence

Follow one value from a Granite UI Resource through Sling POST, JCR persistence and resilient rendering.

  • 30 minutes online
  • Field-to-browser trace
  • Local Author optional
Observable outcome: each developer can explain what name="./title" creates, locate the stored property and describe the behavior of configured, legacy and empty component states.

Topic summary

An AEM component dialog is more than an authoring form: it is the interface through which authors create durable repository content. A field’s label affects the editor experience, but its name determines the property or child Resource that Sling POST persists and that HTL, Sling Models and integrations must continue to understand.

For that reason, changing a field’s stored name, type or shape is a schema change. A safe implementation traces one value from the dialog definition through the HTTP request and JCR persistence to the rendered output, then verifies current, legacy and empty states instead of testing only a successful save.

  • Three Resources: the component under /apps defines capability, cq:dialog defines the authoring UI, and the component instance under /content stores authored values.
  • Granite UI: dialog fields and containers are Sling Resources selected by sling:resourceType; their properties configure the server-rendered authoring controls.
  • Relative persistence: a field named ./title submits title relative to the selected component Resource, so the property is stored beside its sling:resourceType.
  • Runtime contract: HTL and Sling Models read the authored Resource, not the dialog definition. The persisted property name is therefore part of the component API.
  • Compatibility: renaming title to heading does not migrate existing content. Safe evolution may require a fallback, an explicit migration and later removal of the legacy path.
  • Resilience: dialog validation helps new authoring but cannot constrain old, imported or programmatically created content; runtime code must handle missing and unexpected values safely.

Architect preparation

  • Prepare one component dialog definition or use the supplied Granite UI Resource diagrams.
  • Use the same example value throughout the dialog, request, repository and output trace.
  • Prepare current, legacy and empty stored states without depending on a live edit.
  • Keep filesystem encoding such as _cq_dialog/.content.xml separate from the JCR path cq:dialog.

Learning objectives

  • separate component definition, dialog Resource and authored component instance;
  • read a Granite UI field definition and its relevant properties;
  • trace a relative field name through Sling POST to JCR and HTL;
  • identify when a dialog change requires compatibility and migration work.

  3. Identify the HTL or model access point and the resulting DOM.
