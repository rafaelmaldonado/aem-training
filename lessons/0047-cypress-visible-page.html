Class 47 · Week 10 · October 20, 2026

Cypress integration testing

Specify and verify one Author → Publish → visitor journey.

  • 30-minute technical session
  • 10 downloadable PNG slides · Spanish presenter notes
  • Guía completa en español
Observable result: a known title is saved in Author, published with its page, and found on Publish by a browser acting as a visitor. The class uses this one route to explain reliable Cypress integration tests.

The technical spec comes first: target environment, preconditions, action, assertion and evidence. TrainingMessage HTL and the Cypress example apply that spec to a small AEM page. Authoring and publication prepare the fixture; Cypress automates the anonymous visitor check.

Slide deck

Present the editable web slides, download or copy a PNG, or print the deck to PDF. Expand the Spanish notes for facilitation.

Notas para LLM · slide 01

Conectar con la sesión 46: el test unitario observa el getter; una prueba de integración de navegador observa la página entregada. Hoy se elige una ruta crítica y se define qué evidencia debe producir. El ejemplo TrainingMessage sólo concreta el contrato.

Notas para LLM · slide 02

Fijar una sola ruta: título autorado, página publicada y resultado en Publish. No llamar automatización de UI de autor a lo que aquí es fixture preparado. Si se necesita verificar los clics del editor, sería otra prueba con otro riesgo. El visitante no usa credenciales de Author.

Notas para LLM · slide 03

Pedir al grupo que identifique riesgo, precondición, acción, aserción y evidencia antes de mostrar código. Un 200 sin el título no cumple el contrato; un título en Author tampoco prueba Publish. La URL exacta y la versión de contenido hacen interpretable el resultado.

Notas para LLM · slide 04

Usar una página desechable con una sola instancia del componente. El ejemplo añade data-cy al section del HTL sin cambiar su texto. El texto del título es justo lo que se quiere comprobar, así que se compara explícitamente. Evitar selectores por nth-child o clases de presentación.

Notas para LLM · slide 05

El aislamiento por defecto de Cypress limpia el contexto del navegador antes de cada prueba E2E. No revierte el repositorio AEM ni despublica contenido. Un caso que sólo pasa después de otro tiene una dependencia de estado. Para esta clase hay un único it y la página se prepara fuera de la ejecución.

Notas para LLM · slide 06

Mostrar el spec completo en la guía si piden setup. publishPageUrl debe ser la URL de Publish, con el título esperado de la versión publicada. cy.visit falla con respuestas no exitosas y las aserciones reintentan el estado del DOM. No usar una espera fija para compensar una publicación incompleta.

Notas para LLM · slide 07

Una prueba intermitente no siempre es problema de Cypress. Separar fixture no listo, publicación antigua, selector inestable, dependencia entre tests y carga asíncrona. Repetir el mismo caso y comparar la primera señal diferente; evitar cy.wait con tiempo fijo como primer arreglo.

Notas para LLM · slide 08

Adobe documenta el módulo ui.tests, empaquetado en Docker, la activación de pruebas UI y reportes JUnit en REPORTS_PATH. El pipeline aporta URLs del ambiente. Un spec copiado sin esa integración no corre como gate. Aquí se ejecuta sólo la práctica local; no atribuirle un resultado de Cloud Manager.

Notas para LLM · slide 09

Pedir al grupo que reconstruya el contrato: precondición publicada, URL, acción visitante, selector, resultado esperado y evidencia. Recalcar que el aislamiento del navegador no limpia AEM y que la ejecución local no es un gate de Cloud Manager.

Notas para LLM · slide 10

Abrir preguntas. Si hace falta, volver al contrato de la slide 3 o a la distinción entre aislamiento del navegador y contenido AEM.
