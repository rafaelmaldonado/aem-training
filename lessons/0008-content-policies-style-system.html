Class 7 · Week 2 · Day 7 · August 25, 2026

Govern authoring choices without changing component code.

Trace policy resolution, control Allowed Components and connect semantic author choices to deployed CSS.

  • 30 minutes online
  • Policy diagrams
  • Local Author optional
Observable outcome: each developer can explain why a component is available or unavailable, trace its cq:policy mapping and show one semantic style backed by deployed CSS.

Topic summary

Content policies are the governance layer between reusable component code and the choices available to authors in a particular template context. The component provides capability; the policy decides how much of that capability is exposed, which components may be inserted and which defaults or semantic styles apply.

This separation lets the same component implementation support different authoring contracts without forks. It also gives developers a precise diagnostic path: when a component works in one template but not another, trace the policy mapping under /conf before changing HTL, Java or client libraries.

  • Capability versus governance: component code defines what is technically possible; policy controls how that capability may be used at one template location.
  • Policy resolution: the template’s policy tree mirrors its component structure, and cq:policy points from a component location to the policy definition under /conf.
  • Allowed Components: deployment makes a component available to AEM, but the container policy determines whether authors may insert it there. Installed does not mean authorable everywhere.
  • Scope: a policy may affect many component instances and templates, so its consumers must be understood before changing it.
  • Configuration versus content: reusable defaults belong under /conf; values that describe one authored instance belong under /content.
  • Style System: a policy exposes a semantic Style Name and maps it to a CSS class. A loaded client library must still implement that class, and the rendered DOM is the evidence that the complete chain works.

Architect preparation

  • Prepare a policy mapping example under /conf; the supplied diagram is sufficient.
  • Choose a small Guide Page component set and one intentionally disallowed component.
  • Prepare one semantic Style Name and its corresponding CSS class.
  • Do not depend on a live policy edit; repository and editor evidence may be captured beforehand.

Learning objectives

  • separate component capability from policy configuration;
  • trace a template location through cq:policy to its policy definition;
  • explain Allowed Components and policy defaults by scope;
  • connect Style Name, CSS class, client library and rendered wrapper.
