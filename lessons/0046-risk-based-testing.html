Class 46 · Week 10 · October 19, 2026

Choose the test that proves the risk

Match unit, HTTP and browser checks to the AEM behavior each one can observe.

  • 30-minute technical session
  • 12 downloadable PNG slides · Spanish presenter notes
  • Guía completa en español
Observable result: choose a test from the risk, its public result and the environment. Explain the difference between a focused Java test and checks of an installed AEM route or effective permission.

A useful test states a risk, the result that exposes it and the expected outcome. In AEM, the same feature can cross a Sling Model, an OSGi service, servlet resolution and repository permissions. Each boundary needs an observer that reaches it. This session maps those observers to unit tests, HTTP checks and browser tests.

The live demo reuses TrainingMessageModel and its existing tests. The other examples come from the course's HTTP service and service-user code; servlet routing is an illustrative case grounded in Sling's resolution rules.

  • State risk, observation, expected result and environment.
  • Use AEM Mocks for focused resource, Model and OSGi behavior.
  • Test adverse service responses with a controlled HTTP stub.
  • Check an installed servlet route by requesting the SDK.
  • Verify service-user access with the effective identity.
  • Reserve a browser check for the user journey it can observe.

Notas para LLM · slide 01

Conectar con la sesión 19: ya escribieron unit tests. Hoy se decide qué riesgo observa cada nivel y dónde termina su evidencia. El caso del título vacío es la demo; servicios OSGi, resolución Sling y ACL muestran cómo se aplica la misma decisión en AEM.

Notas para LLM · slide 02

Definir los cuatro elementos de una afirmación de prueba: riesgo, observación, resultado esperado y entorno. Una aserción sin contrato sólo comprueba una implementación. El entorno limita la conclusión: un getter en AEM Mocks no demuestra una URL instalada.

Notas para LLM · slide 03

Adobe sitúa JUnit en unit tests, pruebas funcionales Java basadas en HTTP en it.tests y pruebas de navegador en ui.tests. Son capas de observación, no una lista que se deba aplicar a cada cambio. La sesión 47 detallará un recorrido UI. Fuentes: estrategia y UI tests.

Notas para LLM · slide 04

El contexto prepara recursos, request y registros OSGi de prueba. RESOURCERESOLVER_MOCK carece de JCR subyacente; JCR_MOCK no soporta todas sus funciones. El mock puede suministrar una policy, pero no reproduce toda la pila de templates y mappings. Fuentes: uso y tipos de resolver.

Notas para LLM · slide 05

Negativo significa entrada o condición adversa con resultado definido; no significa que el test deba fallar. El caso Model usa la sesión 18, el 503 usa la prueba de la 42. El ejemplo de servlet es ilustrativo: el status exacto depende del registro y de la respuesta fallback de la instancia.

Notas para LLM · slide 06

Comparar propiedad ausente con valor presente que trim() deja vacío. Abrir el archivo completo para ver extensión, imports y registro. La aserción observa el contrato del getter público. Este test no renderiza HTL ni responde una URL.

Notas para LLM · slide 07

En el proyecto local: mvn -pl core -Dtest=TrainingMessageTest test. Mutar temporalmente sólo la condición title.trim().isEmpty(); ver el fallo de aserción de la prueba nueva; restaurar y comprobar diff limpio. Un error de Maven, metadata DS o creación del modelo exige corregir setup antes de atribuirlo al fallback.

Notas para LLM · slide 08

El test existente de la sesión 42 inicia un HttpServer local y prueba 200, 401, 503 y timeout. Es un ejemplo de prueba de servicio con frontera HTTP real pero proveedor controlado; no verifica egress, secreto ni configuración efectiva del SDK. Fuente local: ExternalStatusServiceTest.

Notas para LLM · slide 09

Ejemplo ilustrativo: no hay servlet status nuevo en este repo. Sling parte del recurso y su sling:resourceType; selectores, extensión y método participan en la resolución. Probar doGet con request mock valida la lógica, no el registro ni qué handler gana en la instancia. Fuente: Apache Sling.

Notas para LLM · slide 10

La prueba de la sesión 29 verifica que se pide training-guide-read y se cierra sólo el resolver propio. No carga la configuración de mapping ni las ACL de Repo Init. En el SDK, comprobar acceso efectivo con la identidad técnica real; registrar el resultado de rutas de práctica permitidas y supuestamente restringidas, pues puede haber permisos heredados. Fuentes: test y Adobe · service users.

Notas para LLM · slide 11

Pedir una elección de prueba para cuatro riesgos: fallback del Model, clasificación de 503 en el servicio, resolución de un servlet y permiso efectivo. Para cada uno, el grupo nombra lo observado y el límite. El recorrido de navegador se desarrolla en la sesión 47.

Notas para LLM · slide 12

Abrir preguntas. Volver al caso del título o al límite del mock si hace falta. Cerrar sin introducir un tema nuevo.
