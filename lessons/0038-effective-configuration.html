Explain effective configuration

Trace a service value from its PID and run mode to the environment value it receives.

  • 30-minute technical session
  • 9 PNG slides

Slide deck

Copy each PNG to PowerPoint or download it below. The local and Cloud values shown are illustrative. Open the presenter note under each slide to prepare its explanation.

Notas para explicar la slide 01
  • Propósito: plantear la pregunta de la sesión: qué configuración recibe realmente un servicio en un ambiente concreto.
  • Explica: seguirás la ruta del PID al archivo que gana, y de sus placeholders al valor efectivo. Los ejemplos locales permiten razonar sobre Cloud sin acceso a una cuenta.
  • Prepara: presenta el servicio ficticio CatalogService que aparecerá después y anuncia una sesión de 30 minutos con preguntas al final.
Download PNG
Notas para explicar la slide 02
  • Propósito: conectar el nombre del archivo .cfg.json con la identidad del servicio que configura.
  • Explica: el PID de un servicio suele coincidir con el nombre completo de su clase. En una configuración factory, el sufijo después del PID distingue una instancia; la carpeta indicará a qué run modes se aplica.
  • Prepara: señala por separado el PID, el nombre de instancia east y la extensión. Los nombres com.acme... son didácticos, no archivos de este proyecto.
Download PNG
Notas para explicar la slide 03
  • Propósito: mostrar que la selección entre carpetas ocurre por PID completo, no por propiedad individual.
  • Explica: en Author con dev coinciden config.author y config.author.dev; gana la segunda. Su archivo no hereda timeout=1000 del primero. El valor que quede sin definir dependerá del componente.
  • Prepara: pide primero que identifiquen la carpeta ganadora. Después compara los dos pequeños archivos y señala el timeout ausente.
Download PNG
Notas para explicar la slide 04
  • Propósito: decidir de dónde proviene cada valor de una configuración OSGi.
  • Explica: usa un valor inline y versionado en Git como opción habitual. Usa $[env:...] para un valor no secreto que deba variar entre ambientes de desarrollo o Preview. Usa $[secret:...] para toda clave o contraseña; el valor real queda fuera de Git.
  • Prepara: usa únicamente URL y clave ficticias. Pide que clasifiquen timeout, url y apiKey antes de revelar cada columna.
Download PNG
Notas para explicar la slide 05
  • Propósito: reproducir localmente la selección author,dev y la sustitución de una variable no secreta.
  • Explica: exporta CATALOG_URL antes de iniciar Java. El SDK arranca con esos run modes y el placeholder del archivo seleccionado recibe el valor de la terminal. El nombre del JAR en la slide es ilustrativo.
  • Prepara: si harás demo, ten el SDK y el paquete de ejemplo instalados y usa una URL ficticia. Si no, recorre los tres pasos como simulación. La configuración de Cloud Manager requiere una comprobación aparte.
Download PNG
Notas para explicar la slide 06
  • Propósito: mostrar el mecanismo local de $[secret:CATALOG_KEY], distinto de la variable exportada en la slide anterior.
  • Explica: el SDK lee un archivo llamado exactamente CATALOG_KEY, sin extensión, desde el directorio definido por org.apache.felix.configadmin.plugin.interpolation.secretsdir en sling.properties. Ese archivo contiene el valor, no el placeholder.
  • Prepara: usa un secreto de prueba sin valor real, crea el archivo y configura la propiedad antes de arrancar el SDK. Mantén el directorio fuera de Git.
Download PNG
Notas para explicar la slide 07
  • Propósito: explicar el caso especial de Preview sin añadir otro run mode de configuración.
  • Explica: Preview hereda el archivo config.publish. El mismo placeholder CATALOG_URL puede recibir un valor distinto si Cloud Manager lo define para Publish o Preview. No se crea una carpeta config.preview.
  • Prepara: lee las dos URL ficticias como un contraste de valores por servicio. Señala que la carpeta y el valor de entorno responden preguntas diferentes.
Download PNG
Notas para explicar la slide 08
  • Propósito: diagnosticar con evidencia por qué el mismo .cfg.json produce valores diferentes en local y Cloud.
  • Explica: en el ejemplo, local resuelve CATALOG_URL y Cloud conserva el placeholder porque no se definió la variable para ese ambiente y servicio. Primero confirma PID y run modes; luego consulta Status → Configurations → Get Status en Developer Console y verifica la variable de Author en Cloud Manager.
  • Prepara: trata los valores como un caso ficticio. Pregunta qué dato revisarían antes de cambiar código. Aclara que la conclusión de variable ausente depende de comprobarla; otras diferencias pueden tener otra causa.

Notas para explicar la slide 09
  • Propósito: cerrar con una explicación completa de la ruta de configuración y abrir preguntas.
  • Explica: resume en una frase: «Identifico el PID, elijo el archivo por run modes, resuelvo su placeholder y verifico la propiedad efectiva en el servicio».
  • Prepara: si no surgen preguntas, pide que expliquen qué archivo gana en Author con dev y dónde comprobarían un valor que difiere de local.
