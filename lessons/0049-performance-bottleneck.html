Measure and fix a performance bottleneck

Find the slow stage, make one change, and measure the same page again.

  • 30-minute technical session
  • 10 downloadable PNG slides · Spanish presenter notes
  • Guía completa en español
Local case: a disposable Sites page on Publish with an intentionally heavy hero image. The figures in the slides are simulated teaching data; record your own results on the actual URL.

Slide deck

Present the web slides, download each PNG, or print the deck to PDF. Expand the Spanish notes for facilitation.

Notas para LLM · slide 01

Conectar con la sesión 48: ahora se mide la rapidez con la que aparece el contenido principal de esa página. El caso tiene una imagen pesada preparada para practicar; no afirma que WKND o Core Image sean lentos por defecto. Los números mostrados más adelante son simulados.

Notas para LLM · slide 02

Definir LCP y TTFB antes de interpretar cifras. El presupuesto 3,0 s y 300 kB es una elección didáctica para un escenario local específico, no un estándar general de AEM. Pedir que identifiquen el elemento LCP en la traza; no asumir que siempre es la imagen. Fuente: web.dev · Optimize LCP y Chrome · Network timing.

Notas para LLM · slide 03

La primera fila representa capas de respuesta; la segunda, recursos y trabajo tras recibir HTML. En SDK local CDN y Dispatcher pueden no existir. TTFB del navegador incluye ida y vuelta de red y espera de respuesta; correlacionar con request.log de Publish antes de culpar una consulta. Si existe Dispatcher, observar hit/miss y elegibilidad con su configuración y logs. Fuentes: Adobe · Caching y Chrome · Network timing.

Notas para LLM · slide 04

Usar DevTools Performance y Network en la URL de Publish. Registrar versión de Chrome, perfil de red y CPU, estado de caché y cinco cifras individuales. Un calentamiento reduce el efecto de primer arranque del entorno; no incluirlo en la mediana. Las métricas de laboratorio fluctúan; si la diferencia es pequeña frente a la variación, medir más. Fuente: Chrome · Lighthouse.

Notas para LLM · slide 05

La gráfica es una comparación ilustrativa de valores, no una línea de tiempo acumulativa ni una medición real. LCP de 3,6 s supera el presupuesto del laboratorio. El TTFB es pequeño frente al recorrido; la imagen LCP transfiere 1,6 MB y tarda 1,9 s. Estas cifras sugieren probar el asset, pero una reducción de bytes no garantiza una mejora de LCP si domina otra etapa. Fuente: web.dev · Optimize LCP.

Notas para LLM · slide 06

No cambiar varias capas a la vez. Para backend, correlacionar con request.log; sólo revisar plan de consulta cuando haya evidencia de una consulta cara. Dispatcher requiere estar presente y permitir observar hit/miss. En el caso preparado se continúa por la fila de imagen, pero cada participante debe verificar su traza. Fuentes: Adobe · Slow Queries, Adobe · Dispatcher Debug y Adobe · Client Libraries.

Notas para LLM · slide 07

En Author cambiar sólo el asset del Core Image por una variante visualmente equivalente. Comprobar encuadre, nitidez y alt; publicar dependencias. Registrar la URL, formato, dimensiones y bytes que realmente recibió Publish. El servicio Web-Optimized Image Delivery existe en AEM Cloud, no en localhost; el SDK local puede usar Adaptive Image Servlet. Fuentes: Adobe · Core Image y Adobe · Web-Optimized Image Delivery.

Notas para LLM · slide 08

Estos son datos simulados. Bajo el protocolo del ejemplo, se cumplen los límites y TTFB queda parecido, lo que apoya la hipótesis de transferencia de imagen. No presentar la diferencia como resultado de WKND. Una tabla real necesita los cinco valores individuales, condiciones, versión de página y una nota sobre variación. Si el elemento LCP cambia, registrarlo y revisar la nueva etapa dominante.

Notas para LLM · slide 09

El cambio sólo se acepta si cumple el presupuesto acordado sin dañar la imagen ni el contenido. Si bajan bytes pero no LCP, la transferencia mejoró, pero el cuello de botella de LCP persiste. Si el cambio observado cabe dentro de la dispersión de las muestras, repetir o medir en un entorno más controlado. No extrapolar el SDK local a CDN, Dispatcher o usuarios reales.

Notas para LLM · slide 10

Preguntar: ¿un TTFB alto demuestra una consulta lenta? No. ¿Menos bytes garantiza menor LCP? No. ¿Qué condición invalidaría esta corrección? Por ejemplo, que la imagen no fuese el elemento LCP, que la diferencia quedara dentro del ruido o que la variante perdiera calidad. Cerrar con la secuencia línea base → hipótesis → un cambio → nueva medición.
