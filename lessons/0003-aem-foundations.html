Class 1 · Week 1 · Day 1

From author to browser.

Build a shared mental model of AEM Sites before opening its implementation details.

  • 30 minutes online
  • 60–90 minutes practice
  • No breakout rooms
Observable outcome: each contributor can draw and explain how a content change moves from Author to a visitor, and distinguish that flow from a code deployment.

Architect preparation

  • Send the initial setup guide before the session.
  • Open one WKND test page in Author and its Publish URL, if available.
  • Create one shared thread or form for the six diagrams and exit answers.
  • Do not troubleshoot individual installations during the explanation; record blockers for office hours.

Learning objectives

By the end of the session, each contributor can:

  • distinguish Author, Publish, Dispatcher and CDN;
  • separate content publication from code deployment;
  • explain where a content author and visitor interact with the system;
  • form a first hypothesis about the layer responsible for a symptom.

Suggested speaking script

Slide 1 · about 2 minutes

“AEM Sites separates what the experience can do from the content used in that experience. Development creates safe, reusable choices. Authors use those choices repeatedly. Our goal is not to remove governance; it is to let content change without requiring a code release.”

Slide 2 · about 2 minutes

“Author and Publish are separate services with separate audiences. An author can save a valid change and still have no public change. When investigating an incident, always ask which service and which user can reproduce it.”

Slide 3 · about 2 minutes

“Content follows an editorial lifecycle. Saving records work on Author. Publishing distributes approved content. That operation does not compile Java, package components or deploy a client library.”

Slide 4 · about 3 minutes

“A visitor usually reaches delivery layers before Publish. If a cache already has a valid response, Publish may not see the request. This is why a page can be correct on Author and Publish but still appear stale to a visitor.”

Slide 5 · about 3 minutes

“Source code follows a controlled delivery path. A commit is built, tested and deployed. At runtime, the deployed component code reads distributed content and produces the response. Keeping both flows separate is the foundation for every diagnosis in this course.”

Slide 6 · about 2 minutes

“A visitor receives the result of three paths: published content provides values, deployed code renders them and delivery caches decide whether that response can be reused. Name the affected path first; then test the nearest boundary.”

Live demonstration

  1. Open an existing WKND page in Author.
  2. Edit only the text of one component and ask, “Did source code change?”
  3. Use Preview and ask what remains exclusive to Author.
  4. Publish the page if the environment permits it.
  5. Open the Publish URL and compare interface, URL and audience.
  6. Open browser developer tools, select the HTML document request and point to the delivery path.
  7. Ask where CDN and Dispatcher could respond even though neither is visible in the page markup.

If only a local Author SDK is available, demonstrate editing and Preview. Explain Publish with the diagram; do not pretend that a local architecture is a cloud delivery environment.

Asynchronous assignment · Who owns the first check?

Individual work, 60–90 minutes. For every scenario, choose the most likely layer and one inexpensive check that could disprove the hypothesis.

  1. An author saved a title, but the visitor still sees the old value.
  2. A component does not appear in the component browser for one page.
  3. After a deployment, a JavaScript request returns 404.
  4. The page works on Author but fails only on Publish.
  5. The first request is slow and repeated requests are fast.
Instructor feedback guide
  1. Check publication and cache before blaming component rendering.
  2. Inspect template policy and allowed components.
  3. Inspect clientlib generation, public path and deployed artifact, then caching.
  4. Compare configuration, permissions, logs and content between services.
  5. Inspect CDN/Dispatcher/browser cache evidence and response headers before assuming Java latency.

Accept another layer when the contributor proposes a cheap check that can falsify the hypothesis.

Individual evidence

  1. One diagram showing the content flow and code flow in different colors.
  2. A response of no more than 60 words: “Why can a change visible on Author be absent on Publish?”
  3. The first layer and check for scenario 5.
  4. Setup status: ready, or the exact blocked step and error.

Acceptance criteria: the diagram contains both flows, correctly places the five delivery layers and distinguishes save, content publication and code deployment. Record proficiency as not demonstrated, with support, independent or can guide; do not grade visual design.
